# План фазы 4 — движок распределения, уровни 0–3 воронки

> Статус: **утверждён 2026-09-27** (вместе с ответами на вопросы 40–45). Выполняется по шагам 4a → 4b, каждый — отдельный PR с зелёным CI.
> Основа: `docs/roadmap.md` (фаза 4), `docs/allocation-design.md`, ADR-0006, 0008, 0009, 0013, `docs/data-model.md` §5 (`allocation_run`, `allocation_decision`).

## Цель

Движок распределения как чистая детерминированная функция «снимок (ADR-0013) + конфигурация + seed → решение с объяснением» и сквозной сценарий в UI: оператор запускает распределение для своего графика, видит предпросмотр с объяснениями и применяет его. Реализуются уровни 0–3 воронки; уровень 4 — простой метод (жадный в порядке MRV). Точные методы (венгерский, CP-SAT, min-cost flow) и локальный поиск — фаза 5.

## Шаг 4a — движок (`services/allocation`), без интеграции

**Пакет `allocation.engine`** — чистые функции над numpy, без БД и HTTP:
- **Загрузка снимка** в матрицы: `C[P, K]` (допуски, битовые маски), `valid` (сроки допусков), `A[P, T]` (доступность по освобождениям), занятость по уже стоящим нарядам и хвосту истории, шаблон времени ролей (интервал и занятые сутки, ADR-0008).
- **Уровень 0 — декомпозиция.** Два вида задачи, как в legacy:
  - **люди** — заполнить ячейки, которые закрывает само подразделение графика, людьми его поддерева;
  - **подразделения** — решить, кому из прямых дочерних отдать свои ячейки (вопрос 40).
- **Уровень 1 — допустимость векторно:** действующий допуск на дату, свободен во все занятые сутки. Отдых, «≤ 1 наряда в сутки» и лимиты проверяются при каждом выборе с учётом уже принятых решений.
- **Уровень 2 — ёмкость и дефициты:** `cap[K, T]` одним матричным умножением. Строгая проверка выполнимости — максимальный поток «люди → (роль, день)» (`scipy.sparse.csgraph.maximum_flow`). Дефициты объясняются по-русски: «14.11: не хватает 2 человек с допуском к роли „Дневальный“ — все допущенные освобождены или в наряде».
- **Уровень 3 — скоринг:** вектор признаков кандидата:
  - нагрузка с экспоненциальным затуханием в нарядо-сутках × вес наряда (вопросы 42, 43);
  - нагрузка по этому типу наряда;
  - отдельный счётчик нарядов в выходные и праздники;
  - давность последнего наряда;
  - для подразделений — ёмкость и долг прошлых периодов.

  Стоимость `X · w`, веса — в конфигурации (YAML в образе и переопределение на прогон), а не константами в коде.
- **Уровень 4 (простой):** ячейки заполняются в порядке MRV (сначала те, у которых меньше всего допустимых кандидатов), кандидат — с наименьшей стоимостью. Равенства разрешаются детерминированно по seed. Для подразделений — квота пропорционально ёмкости (наибольший остаток), затем жадная расстановка по дням.
- **Закрепления:** закреплённые назначения и ячейки, а также ручные назначения (вопрос 41) не пересматриваются, а учитываются как занятость.
- **Решение:** назначения и делегирования. Для каждого — вектор признаков, ранг, топ-5 альтернатив с признаками и сводка отсева («нет допуска: 12, освобождены: 3, отдых: 5, лимит: 1»). Плюс метрики: закрыто ячеек, недокомплект, нарушения (всегда 0 — движок жёсткие ограничения не нарушает), справедливость — стандартное отклонение, Джини, индекс Джайна, `max − min`.
- **Детерминизм:** одинаковые снимок, конфигурация и seed дают побайтно одинаковое решение (тест сравнивает hash).

**Сервис `allocation`:** FastAPI без предметной БД, `POST /internal/solve` (снимок + конфигурация + seed → решение), синхронно — жадный метод укладывается в секунды. Очередь arq для долгих прогонов появится в фазе 5 вместе с CP-SAT. Зависимости — numpy, scipy (BSD); OR-Tools добавится в фазе 5.

**tools**
- `tools/gen/snapshot.py` — генератор синтетических снимков формата ADR-0013 (размер подразделения, число ролей, плотность допусков, освобождения, длительности нарядов), детерминирован по seed. Он же основа экспериментального стенда фазы 5.
- Бенчмарк движка на снимках 1k / 5k / 20k / 50k человек: время по уровням воронки, память, недокомплект, справедливость → `docs/benchmarks/allocation.md`.

**Тесты:** unit-тесты каждого уровня на маленьких снимках. Свойства на случайных снимках по разным seed: жёсткие ограничения никогда не нарушаются, закрепления не меняются, решение детерминировано. Нулевой недокомплект там, где строгая проверка уровня 2 говорит, что задача выполнима, требовать нельзя — жадный метод может не найти решение. Разница с проверкой выполнимости — метрика для фазы 5.

**Статус шага 4a (2026-09-27): выполнен** (ветка `phase-4a-engine`).
- Сервис `allocation` в compose (без предметной БД), `POST /internal/solve`, настройки по умолчанию — `allocation/config/default.yaml`.
- 32 теста: точечные сценарии на ручных снимках (отдых, «≤ 1 в сутки», MRV, освобождения, сроки допусков, лимиты, пересборка, дефициты, квоты подразделений), свойства на 6 видах случайных снимков, проверка, что проверяльщик ловит подложенные нарушения, HTTP.
- Бенчмарк (`docs/benchmarks/allocation.md`): 750 мест при 1 000 человек — 0,55 с, при 50 000 — 9,5 с, все места закрыты, граница max-flow совпала с результатом; по подразделениям — 0,3–3 с.
- На реальных снимках демо-стенда: 21–68 мест за 7–14 мс, нарушений нет.
- Уточнено по ходу: в снимке у назначений появились id, признак «автоматическое», интервал в минутах и отдых (ADR-0013, версия 1 — у формата ещё не было потребителей); общий Dockerfile собирает сервисы и без миграций.

## Шаг 4b — интеграция: предпросмотр → применение

**scheduling** (`docs/data-model.md` §5):
- `allocation_run` — прогон: график, вид (`people` / `units`), область (весь месяц, диапазон дат или выбранные ячейки), конфигурация, seed, `snapshot_hash`, сжатый снимок (срок хранения — настройка), статус `preview_ready → applied / discarded / stale`, метрики.
- `allocation_decision` — объяснимость на каждую ячейку.
- `POST /schedules/{id}/allocate` — собрать снимок (фаза 3c), вызвать `allocation`, сохранить прогон и решения, вернуть предпросмотр.
- `POST /allocation-runs/{id}/apply` — записать только изменившееся: новые назначения с `source = auto`, делегирование — тем же механизмом, что вручную. Всё в одной транзакции, с аудитом и событиями.
  - Перед записью снимок пересобирается. Если hash изменился (кто-то поменял данные после предпросмотра) — прогон становится `stale`, применение отклоняется, нужно пересчитать (вопрос 45).
  - Каждое назначение ещё раз проходит проверки 3b; ограничение БД остаётся последней защитой.
- `POST /allocation-runs/{id}/discard`, `GET /allocation-runs/{id}` (предпросмотр с объяснениями), `GET /schedules/{id}/allocation-runs` (история прогонов).
- Режимы для людей (как в legacy): **дозаполнить** — только пустые места; **пересобрать автоматические** — движок может заменить свои незакреплённые назначения, ручные и закреплённые не трогает.

**allocation:** внутренний клиент из scheduling (`X-Internal-Token`, таймаут), контейнер в compose.

**frontend**
- В графике — «Распределить людей» и «Распределить по подразделениям»: выбор области и режима, запуск.
- Предпросмотр прямо в таблице: предложенные ячейки подсвечены. Сводка: закрыто, недокомплект с объяснением дефицитов, метрики справедливости. По ячейке — почему выбран этот человек или подразделение: признаки, ранг, альтернативы, сводка отсева. Кнопки «Применить» и «Отменить».
- История прогонов графика.

**Бенчмарк и документы:** сквозное время «снимок → решение → предпросмотр» на демо-стенде и на синтетике; раздел «Реализация уровней 0–3» в `docs/allocation-design.md` с фактическими числами.

## Критерии готовности фазы

- Движок — чистая функция: запускается на синтетическом снимке без сервисов и БД, одинаковый вход и seed дают одинаковое решение (тест).
- Жёсткие ограничения (допуск и его срок, освобождения, «≤ 1 наряда в сутки», отдых, лимиты, закрепления) не нарушаются ни на одном из случайных снимков в тестах свойств.
- Дефициты объясняются человеческим языком до попытки решения. Для каждого предложенного назначения есть объяснение: признаки, ранг, альтернативы, причины отсева.
- Сквозной сценарий в UI на демо-данных: факультет распределяет роль по курсам, курс распределяет людей, предпросмотр показывает объяснения, применение записывает назначения с аудитом, повторное применение устаревшего прогона отклоняется.
- Бенчмарк движка на 1k / 5k / 20k / 50k зафиксирован в `docs/benchmarks/allocation.md`; распределение месяца для подразделения демо-размера — в пределах секунд.
- `just lint`, `just test`, `just e2e` и CI зелёные. Новые e2e: распределение людей с предпросмотром и применением, распределение по подразделениям.

## Что не входит

Венгерский алгоритм, CP-SAT, min-cost flow, MRV + локальный поиск, arq-очередь и сравнение с legacy-baseline на стенде — фаза 5. Печать и дашборды справедливости — фаза 6.

## Вопросы к утверждению

Утверждены предложенные ответы (2026-09-27); они заложены в план выше и отмечены в `docs/open-questions.md` (№40–45).

40. **Распределение по подразделениям** (кому делегировать роли) — в фазе 4 вместе с людьми простым методом или только люди, а подразделения — в фазе 5? *Предложение:* оба вида в фазе 4. Для подразделений — квота пропорционально ёмкости с учётом долга и жадная расстановка по дням. Точные методы (Сент-Лагю + min-cost flow) — в фазе 5.
41. **Ручные назначения при автораспределении.** *Предложение:* ручные всегда считаются закреплёнными — движок их не трогает. Он пересматривает только свои (`auto`) незакреплённые назначения, и только в режиме «пересобрать автоматические».
42. **Затухание нагрузки по умолчанию** (open-questions №14). *Предложение:* период полураспада 30 дней: наряд месячной давности весит вдвое меньше свежего. Точное значение подбирается в экспериментах фазы 5.
43. **Вес наряда в выходной или праздник.** *Предложение:* ×1,5 в общей нагрузке плюс отдельный счётчик праздничных нарядов, который выравнивается отдельно (open-questions №10).
44. **Кто запускает и применяет автораспределение.** *Предложение:* тот же, кто может менять график (действие `update` над графиком). Отдельной роли не вводим.
45. **Данные изменились между предпросмотром и применением.** *Предложение:* применение отклоняется, прогон помечается устаревшим, оператор пересчитывает. Частичного применения поверх изменённых данных нет.
