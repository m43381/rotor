# План фазы 5 — оптимизация уровня 4 и экспериментальный стенд

> Статус: **утверждён 2026-09-27** (вместе с ответами на вопросы 46–50). Выполняется по шагам 5a → 5b → 5c, каждый — отдельный PR с зелёным CI.
> Основа: `docs/roadmap.md` (фаза 5), `docs/allocation-design.md` (уровень 4, «Экспериментальная часть»), ADR-0006, 0008, 0013, итоги фазы 4 (`docs/benchmarks/allocation.md`).

## Цель

Заменить на уровне 4 воронки простой жадный метод фазы 4 точными и улучшающими методами, каждый — на своём размере задачи. Сделать долгие расчёты фоновыми. Получить экспериментальное сравнение методов со старым алгоритмом (legacy) на 1k / 5k / 20k / 50k человек и глубоком дереве. Таблицы и графики должны годиться для главы диплома без доработки.

Жадный MRV фазы 4 остаётся: он даёт начальное решение и подсказку для точных методов, и он же — участник сравнения.

## Шаг 5a — методы уровня 4 в движке

Все методы — в `allocation.engine`, чистые функции с тем же входом и выходом: снимок + конфигурация + seed → решение с объяснением. Жёсткие ограничения соблюдаются всегда. Каждое решение сверяется независимой проверкой (`engine/verify.py`) в тестах свойств.

**Люди по ячейкам**
- **Венгерский алгоритм по дням** (`scipy.optimize.linear_sum_assignment`). Точный оптимум по стоимости на каждый день: матрица «места дня × допустимые люди», стоимость — признаки уровня 3. Дни решаются по порядку, решение дня входит в состояние следующего (отдых, лимиты, нагрузка). Глобального оптимума за месяц метод не даёт — это и показывает эксперимент.
- **MRV + локальный поиск.** Жадное решение улучшается ограниченное время:
  - обмен людей между двумя назначениями;
  - перенос места на свободного допустимого человека;
  - имитация отжига с детерминированным генератором по seed.

  Для больших подзадач, где точный решатель не укладывается во время.
- **OR-Tools CP-SAT на месяц подразделения.** Классическая постановка Nurse Rostering. Булевы переменные «человек × ячейка» — только для допустимых пар уровня 1.
  - **Жёсткие ограничения:** численность, «≤ 1 наряда в сутки» (по занятым суткам), отдых (пары ячеек, нарушающие его, взаимоисключающие), лимиты, закрепления как константы.
  - **Подсказка:** жадное решение передаётся решателю как hint.
  - **Цель** — лексикографическая (вопрос 49): сначала как можно больше закрытых мест, затем равномерность нагрузки с учётом истории, затем стоимость признаков.
  - **Детерминизм:** фиксированный seed и ограничение по «детерминированному времени» решателя (`max_deterministic_time`) вместо настенного. Одинаковый вход даёт одинаковый результат на той же версии OR-Tools.
- **Скользящий горизонт.** Если подзадача месяца слишком велика для CP-SAT, месяц решается окнами по 7–10 дней с перекрытием. Решения прошлых окон и хвост прошлого месяца фиксированы как контекст (`docs/allocation-design.md`, «Скользящий горизонт»).

**Ячейки по подразделениям**
- Квоты — метод **Сент-Лагю** вместо наибольшего остатка, веса — ёмкость с поправкой на долг, как в фазе 4.
- Расстановка по дням — **min-cost flow** (OR-Tools `SimpleMinCostFlow`): подразделение с квотой → (роль, день) → сток. Стоимость учитывает занятость подразделения в эти сутки и запас людей. Точный оптимум за полиномиальное время.

**Выбор метода** (вопрос 46): `method: auto | greedy | hungarian | local_search | cpsat` в конфигурации. `auto` выбирает по размеру подзадачи (число допустимых пар «человек × ячейка»), пороги берутся из бенчмарка. В решении записано, каким методом и с какими пределами оно получено; если точный метод не успел, отмечено, что это лучшее найденное, а не оптимум.

**Объяснимость:** признаки, альтернативы и сводка отсева — как в фазе 4 для любого метода. Для CP-SAT и min-cost flow «альтернативы» — лучшие кандидаты по стоимости признаков, а не шаги поиска.

**Зависимость:** `ortools` (Apache 2.0), колёса ставятся в образ, интернет во время работы не нужен.

**Статус шага 5a (2026-09-27): выполнен** (ветка `phase-5a-methods`).
- Методы: венгерский по дням, локальный поиск с отжигом, CP-SAT (двухэтапная цель, подсказка локального поиска, сужение модели, окна), для подразделений — Сент-Лагю и min-cost flow; общее объяснение повтором решения для любого метода; режим `auto`.
- Тесты allocation — 52: каждый метод соблюдает жёсткие ограничения и детерминирован; улучшающие методы не теряют мест; локальный поиск улучшает равномерность; `auto` останавливается, когда покрытие доказано границей max-flow; квоты Сент-Лагю и наибольшего остатка на классическом примере.
- Главные выводы (`docs/allocation-design.md`, «Реализация уровня 4»): равномерность лучше всех выравнивает локальный поиск (σ нагрузки 1,42 → 0,85 на 300 человек за 0,6 с); CP-SAT за секунды почти не улучшает его, но при нехватке людей закрывает больше мест (401 против 381); венгерский по дням при нехватке закрывает больше жадного (465 против 422). Отсюда устройство `auto`.
- Найдено и исправлено: объяснение описывало все альтернативы, а не пять — замедление в 4,6 раза; в hash решения попадало настенное время CP-SAT.
- Бенчмарк методов на 1k–50k — `docs/benchmarks/allocation.md`; пороги `auto` по умолчанию: CP-SAT — до 60 тыс. допустимых пар, локальный поиск — до 2 млн, дальше жадный.

## Шаг 5b — фоновые расчёты и выбор метода в UI

- **Очередь arq на Redis** (`docs/architecture.md` §3.4). `POST /internal/solve` остаётся синхронным для маленьких задач. Для больших добавляются `POST /internal/jobs` и `GET /internal/jobs/{id}` (статус, прогресс, результат); воркер — отдельный контейнер.
- **scheduling:** у прогона появляются статусы `queued` и `running` (они уже есть в модели данных). Прогон создаётся сразу, решение и объяснения сохраняются, когда задача готова. Если allocation недоступен, задача ждёт в очереди, а UI показывает «ожидание движка» (`docs/architecture.md` §5).
- **Пределы времени** (вопрос 47): синхронный расчёт — до 10 с, фоновый — до 60 с. Окончательные значения фиксируются по бенчмарку этой фазы; это закрывает НФТ «распределение на месяц укладывается в секунды».
- **UI:** выбор метода в диалоге («Автоматически» по умолчанию; конкретный метод — для суперадминистратора), индикатор хода фонового расчёта, в предпросмотре — какой метод применён и получен ли оптимум.

**Статус шага 5b (2026-09-27): выполнен** (ветка `phase-5b-jobs`).
- allocation: очередь arq (`allocation-worker` в compose), `POST /internal/jobs` и `GET /internal/jobs/{id}`; результат хранится сутки. Тест — на настоящем Redis с воркером в процессе, включая упавшую задачу.
- scheduling: прогон в фоне, если в снимке больше `allocation_async_people` (3 000) человек или явно выбран CP-SAT; фоновому CP-SAT даётся `allocation_async_time_limit_s` (60 с). Прогон создаётся «в очереди», результат забирается при запросе прогона — ровно один раз, под блокировкой строки. Применить незавершённый нельзя, отменить можно. Метод, кроме «автоматически», выбирает только суперадминистратор.
- UI: выбор метода в диалоге (суперадминистратор), индикатор «в очереди / идёт расчёт» с опросом, в предпросмотре — метод и «закрыто максимально возможное число мест — доказано» или «оптимальность не доказана».
- На демо-стенде: CP-SAT для курса в фоне — 32 с, все 68 мест, покрытие доказано.
- Внутренний HTTP-клиент умеет GET; arq ограничивает redis-клиент версией 5.x — код Streams с ней совместим, все тесты зелёные.
- e2e сценарий делегирования больше не зависит от того, стоят ли люди в выбранных ячейках демо-стенда.

## Шаг 5c — экспериментальный стенд (материал главы диплома)

- **Legacy-baseline.** Алгоритмы старой системы — распределение нарядов по подразделениям (`PlanAutomationService`) и людей по нарядам (`AssignmentAutomationService`) — переносятся на снимок в памяти, без ORM и сети. Сравнение идёт по алгоритму, а не по инфраструктуре (`docs/legacy-analysis.md` §2.4–2.5). Код не копируется — повторяется логика: порядок обхода, счётчики, веса, сортировка, мягкий штраф за соседние дни. Нарушения, которые legacy допускает (отдых как штраф, а не запрет), считаются отдельно.
- **Генератор деревьев** 6+ уровней и тысяч узлов (основной профиль, open-questions №4): иерархический прогон сверху вниз — распределение по подразделениям на каждом уровне, затем люди в листьях. Это и есть декомпозиция уровня 0 на всей организации.
- **Сравнение** на 1k / 5k / 20k / 50k человек и нескольких seed:
  - методы: legacy, жадный MRV, MRV + локальный поиск, венгерский по дням, CP-SAT;
  - для подразделений: legacy, наибольший остаток + жадный, Сент-Лагю + min-cost flow;
  - метрики: время, пик памяти, недокомплект и расстояние до строгой границы max-flow, нарушения (у legacy), справедливость — стандартное отклонение, Джини, Джайн, размах; отдельно для праздничных нарядов.
- **Подбор затухания нагрузки** (открытая часть open-questions №14): симуляция 6 месяцев подряд с полупериодом 14 / 30 / 60 / 90 дней. Выбирается значение, лучше всего выравнивающее нагрузку на длинном горизонте без резких перекосов в отдельном месяце; оно становится значением по умолчанию.
- **Результаты** — `docs/experiments.md`: таблицы и графики (PNG, matplotlib только в инструментах стенда, не в образах сервисов), методика, выводы по каждому методу и порогам выбора. Всё воспроизводится одной командой `just experiment`.

## Критерии готовности фазы

- Все методы соблюдают жёсткие ограничения на случайных снимках (тесты свойств с независимой проверкой), закрепления и ручные назначения не трогают, детерминированы по seed.
- CP-SAT на подзадаче подразделения демо-размера закрывает не меньше мест, чем жадный метод, и не хуже его по справедливости. Где проверка уровня 2 показывает, что задача выполнима, недокомплект CP-SAT равен нулю в пределах времени.
- Долгий расчёт идёт в фоне: UI показывает статус, результат открывается как обычный предпросмотр.
- `docs/experiments.md` содержит таблицы и графики сравнения по времени, памяти, недокомплекту и справедливости на 1k–50k и глубоком дереве. Всё воспроизводится `just experiment`.
- Пределы времени расчёта зафиксированы по бенчмарку (НФТ «распределение на месяц — в секундах»).
- `just lint`, `just test`, `just e2e` и CI зелёные.

## Что не входит

Автоматический каскад по всему поддереву из UI (одной кнопкой сверху вниз) есть только на стенде эксперимента — в интерфейсе каждое подразделение по-прежнему распределяет своё (вопрос 50). Печать и дашборды справедливости — фаза 6.

## Вопросы к утверждению

Утверждены предложенные ответы (2026-09-27); они заложены в план выше и отмечены в `docs/open-questions.md` (№46–50).

46. **Выбор метода.** *Предложение:* по умолчанию автоматически по размеру задачи с порогами из бенчмарка. Конкретный метод может выбрать суперадминистратор (для экспериментов и разбора случаев); операторы видят, каким методом получено решение.
47. **Время расчёта.** *Предложение:* синхронно до 10 с, в фоне до 60 с; окончательные значения фиксируются по бенчмарку. Если точный метод не успел, применяется лучшее найденное решение с пометкой «не доказано оптимальным».
48. **Невыполнимая задача** (людей не хватает на все места). *Предложение:* движок никогда не нарушает отдых и лимиты сам (open-questions №8, 9) — места остаются незакрытыми с объяснением дефицита, а нарушение с комментарием оператор может сделать вручную. Режима «ослабить ограничения ради комплекта» нет.
49. **Цель оптимизации.** *Предложение:* лексикографическая: сначала максимум закрытых мест, затем равномерность нагрузки (сумма квадратов отклонений нагрузки с учётом истории, праздничные — отдельным слагаемым), затем стоимость признаков уровня 3. Мин-макс нагрузки — в сравнении на стенде, не по умолчанию.
50. **Каскад по всему поддереву.** *Предложение:* в фазе 5 — только на экспериментальном стенде. В интерфейсе каждое подразделение распределяет своё, как в реальном процессе делегирования. Кнопку «распределить всё поддерево» можно добавить позже отдельным решением.
