# План фазы 6 — `documents` и `analytics`: импорт, печать, дашборды

> Статус: **утверждён 2026-09-27** (вместе с ответами на вопросы 51–58). Выполняется по шагам 6a → 6b → 6c, каждый — отдельная ветка и PR с зелёным CI.
> Основа: `docs/roadmap.md` (фаза 6), `docs/architecture.md` §3.5–3.6, open-questions №15–16, ADR-0001 (границы сервисов), ADR-0004 (события), ADR-0010 (аудит), ADR-0011 (проекции подразделений), ADR-0012 (лицензии фронтенда).

## Цель

Сделать систему пригодной для работы с реальными данными и бумажным документооборотом:
- наполнять личный состав, допуски и освобождения из xlsx/csv по шаблону — с предпросмотром и отчётом об ошибках до применения;
- печатать обязательные формы: график нарядов на месяц, суточную ведомость, отчёт по нагрузке. Шаблоны расширяемые и заменяются без правки кода;
- видеть на дашборде нагрузку и справедливость по своему поддереву.

В legacy нет ни импорта, ни печати: это новая функциональность, бизнес-правила старой системы здесь не меняются.

Появляются два сервиса целевой схемы (CLAUDE.md): `documents` и `analytics`. Отдельный сервис для каждой задачи не вводится.

## Сквозное решение: чьими правами сервисы читают чужие данные (ADR-0014)

`documents` и `analytics` читают данные других сервисов для конкретного оператора: печать графика, импорт в его подразделения, отчёт по его поддереву. Возможны два варианта.

- **А. Внутренние batch-эндпоинты со служебным токеном**, как у `scheduling` → `personnel`. Тогда `documents` сам проверял бы scope оператора, то есть дублировал бы политику чужих данных.
- **Б (предлагается). Вызов публичного API владельца от имени оператора.** `documents` передаёт JWT оператора дальше (on-behalf-of). Права и аудит проверяет сервис-владелец данных, как при работе из UI. В журнале аудита оказывается реальный оператор, а не служебная учётная запись.

По варианту Б у `documents` не будет своей копии политики. Новые эндпоинты у владельцев — это пакетные операции в их публичном API (импорт в `personnel`), а не обходные внутренние пути.

`analytics` строит собственную read-model по событиям и проверяет scope сам, по проекции подразделений (как все сервисы, ADR-0011) и общей политике из `libs/common`.

## Шаг 6a — импорт (сервис `documents`, пакетный API в `personnel`)

**Сервис `documents`** (FastAPI, своя БД `documents_db`) хранит только служебное состояние: задачи импорта и настройки документов (шаг 6b). Предметные данные остаются у владельцев. В compose добавляются `documents` и маршрут `/api/documents/` в gateway.

**Шаблоны xlsx для заполнения** (openpyxl, MIT) — личный состав, допуски, освобождения:
- лист «Инструкция»;
- выпадающие списки из справочников в пределах scope оператора: подразделения, звания, должности, роли нарядов, виды освобождений;
- проверка дат и обязательных полей средствами Excel.

**Загрузка:**
- xlsx или csv; кодировка csv (UTF-8 или cp1251) и разделитель (`;` или `,`) определяются автоматически;
- до 20 000 строк.

`documents` разбирает файл и проверяет структуру: столбцы, типы, даты, дубликаты внутри файла. Бизнес-проверки делает `personnel`, отдельным пакетным вызовом в режиме «только проверить».

**`personnel`: пакетный импорт в публичном API.** Эндпоинты `POST /imports/{people|clearances|exemptions}` с флагом `dry_run`:
- права — по политике, как для одиночных операций;
- ответ по каждой строке: создать / обновить (было → стало по полям) / без изменений / ошибка с текстом и столбцом;
- применение — одна транзакция, аудит и события на каждую изменённую запись (ADR-0010, ADR-0004);
- данные загружаются пачкой, без N+1.

**Предпросмотр → применение** (тот же контракт, что у распределения):
- задача импорта хранит файл, разобранные строки, отчёт и хэш состояния;
- применить можно только непротухший предпросмотр: перед применением `personnel` повторяет проверку, и при расхождении ответ — «данные изменились, проверьте заново»;
- отчёт об ошибках скачивается как xlsx: исходные строки плюс столбец «Ошибка» с подсветкой ячеек;
- задачи старше 7 дней удаляются вместе с файлами.

**UI:** раздел «Импорт» — мастер из шагов: скачать шаблон → загрузить → предпросмотр с фильтром по ошибкам и сводкой → применить.

**Тесты:** разбор xlsx и csv (кодировки, разделители, битые файлы); пакетные операции `personnel` на Postgres (scope, дубликаты, личный номер); e2e — импорт шаблона с ошибкой, исправление, применение.

**Статус шага 6a (2026-09-27): выполнен** (ветка `phase-6a-import`).
- `personnel`:
  - `GET /imports/{kind}/template` — столбцы и значения выпадающих списков в пределах scope;
  - `POST /imports/{kind}` — проверка или применение. Сопоставление — по личному номеру, без номера — по ФИО и подразделению; права — по каждой строке; «всё или ничего» либо «только корректные»; хэш предпросмотра. Одна транзакция, аудит с комментарием «Импорт» и события на каждую запись.
- Сервис `documents`:
  - БД `documents_db`, таблица `import_job`;
  - xlsx-шаблоны: скрытый лист списков, форматы дат, инструкция;
  - разбор xlsx и csv (UTF-8 или cp1251; разделитель `;`, `,` или табуляция);
  - отчёт xlsx с подсветкой ошибок;
  - применение с автоматической перепроверкой, если данные изменились.
- Доступ к `personnel` — от имени оператора: ADR-0014, клиент `dutyflow_common.upstream`. Отдельный ресурс политики `import` не понадобился: права проверяются по каждой строке существующими правилами `person`, `clearance`, `exemption`.
- В compose добавлен сервис `documents`, в gateway — маршрут `/api/documents/` (таймаут 180 с). В интерфейсе — раздел «Импорт» (не показывается наблюдателю).
- Замеры (`just bench-import`, `docs/benchmarks/import.md`) для 20 000 строк: разбор xlsx — 1,1 с, предпросмотр — 1,1 с, применение — 13 с.
- Тесты:
  - personnel — 6 (создание и изменение, дубликаты, устаревший предпросмотр, права по строкам, допуски вопреки требованиям, освобождения с пересечениями, 2 000 строк);
  - documents — 5 (шаблон, разбор, отчёт, применение, битые файлы);
  - e2e — 3.

## Шаг 6b — печать (`documents`)

**Формы** (open-questions №15):
1. **График нарядов на месяц** — PDF и XLSX. Строки — дни, столбцы — наряды и роли. Если ролей много, таблица разбивается на листы по нарядам. В ячейке — звание и фамилия с инициалами. Выходные и праздники выделены.
2. **Суточная ведомость на дату** — PDF и DOCX (вопрос 53). Наряды → роли → люди: звание, ФИО, подразделение, время заступления.
3. **Отчёт по нагрузке за период** — PDF и XLSX: по людям и по подразделениям — число нарядов, нарядо-сутки × вес, праздничные, показатели справедливости. Данные берутся из `analytics` (шаг 6c), поэтому форма включается после него.

**Реквизиты** (вопрос 52) хранятся в `documents_db` по подразделениям и правятся в UI:
- «УТВЕРЖДАЮ»: должность, звание, ФИО, дата;
- составитель;
- подписи.

**Шаблоны** (вопрос 51):
- **PDF:** HTML-шаблоны Jinja2 → WeasyPrint (BSD). Jinja работает в песочнице (`SandboxedEnvironment`): загруженный шаблон не может выполнить код или прочитать файлы.
- Встроенные шаблоны лежат в образе. Суперадминистратор может загрузить свой шаблон формы с предпросмотром на данных демо-стенда. Шаблоны версионируются, откат к встроенному — одной кнопкой, все замены попадают в аудит.
- **XLSX и DOCX** (openpyxl, python-docx — MIT) формируются кодом по той же модели данных формы; реквизиты подставляются из настроек.

**Шрифты:** PT Astra Serif и PT Astra Sans (OFL) лежат в образе — внешних шрифтов нет. WeasyPrint требует системных библиотек (pango), они ставятся в образ `documents`. Локальные тесты проверяют модель данных формы и HTML; сам PDF проверяется в контейнере (CI и e2e).

**Данные формы** собираются вызовами API `scheduling`, `personnel` и `org` от имени оператора: таблица месяца и назначения с именами — пачкой. График берётся в текущем статусе, а в шапке у черновика печатается пометка «ПРОЕКТ».

**UI:** кнопки «Печать» в графике (месяц, выбранный день, формат) и страница «Реквизиты документов».

**Тесты:** модель данных каждой формы на синтетике; разбиение широких таблиц; песочница шаблонов (попытка доступа к атрибутам и файлам отклоняется); e2e — скачивание PDF и XLSX графика демо-стенда.

## Шаг 6c — аналитика (`analytics`) и дашборды

**Read-model по событиям** (ADR-0004; своя БД `analytics_db`, консьюмер как в `scheduling`/`personnel`):
- **Факт наряда:** назначение, человек, подразделение-исполнитель, подразделение графика, тип и роль, дата, занятые сутки, вес, выходной или праздник, источник (ручное или автоматическое). Создаётся по `assignment.created`, удаляется по `assignment.removed`. Статус графика (`schedule.published`) определяет, что считается фактом (вопрос 57).
- Проекция подразделений (ltree) для фильтра по поддереву — общий код проекций из `libs/common`.
- **Обогащение событий `scheduling`:** в `assignment.*` добавляются занятые сутки, вес роли, признак выходного и источник. Поля добавляются, а не меняются, так что совместимость сохраняется.
- **Начальное заполнение:** события, опубликованные до появления `analytics`, в потоке могут быть уже обрезаны. `scheduling` получает внутренний эндпоинт выгрузки назначений за период пачками, а `just analytics-rebuild` перестраивает read-model с нуля. Повторная доставка событий эффекта не имеет (`processed_event`).

**API** (scope — как у личного состава, вопрос 56):
- `GET /metrics/load` — по людям и дочерним подразделениям за период;
- `GET /metrics/fairness` — σ, Джини, Джайн, размах, отдельно праздничные; формулы — те же, что в движке и в `docs/experiments.md`;
- `GET /metrics/trend` — по месяцам.

Дефициты — незакрытые места текущих графиков — отдаёт `scheduling` из таблицы месяца. Дублировать ячейки в `analytics` незачем.

**Дашборд** (Apache ECharts через vue-echarts, Apache-2.0; проверка лицензий фронтенда — ADR-0012):
- выбор подразделения поддерева и периода;
- карточки справедливости;
- распределение нагрузки по людям (гистограмма) и самые загруженные / недогруженные;
- сравнение дочерних подразделений (нагрузка на допущенного человека);
- тренд по месяцам;
- праздничные наряды отдельно;
- дефициты текущего месяца со ссылкой в график.

**Тесты:** обработчики событий, в том числе повторы и порядок; метрики сверяются с `allocation.engine.metrics`; scope; e2e — дашборд демо-стенда после распределения и публикации.

## Изменения модели данных и сервисов

- Новые БД `documents_db` и `analytics_db` создаются в `db-init`, у каждой свои миграции Alembic.
- Новые контейнеры `documents` (и `documents-worker`, если генерация в фоне понадобится по замерам) и `analytics` + `analytics-consumer`; маршруты в gateway.
- `personnel` — пакетный импорт (без изменения таблиц).
- `scheduling` — обогащение событий и выгрузка для перестроения.
- Политика `libs/common`: ресурсы `import` (create), `document` (read), `document_settings` (read, update), `document_template` (update — только суперадминистратор), `analytics` (read).
- Модель данных — в `docs/data-model.md`. ADR-0014 (доступ от имени оператора, read-model аналитики) и ADR-0015 (печать: HTML-шаблоны в песочнице, WeasyPrint, шрифты в образе) пишутся на шагах 6a и 6b.

## Критерии готовности фазы

- Оператор скачивает шаблон, заполняет его, загружает и видит предпросмотр с ошибками по строкам. После исправления применяет импорт — всё в пределах своего scope, с аудитом.
- Утверждённый график печатается в PDF и XLSX, суточная ведомость — в PDF и DOCX, отчёт по нагрузке — в PDF и XLSX, с реквизитами подразделения. Загруженный суперадминистратором шаблон меняет PDF без правки кода, откат работает.
- Дашборд показывает нагрузку и справедливость по поддереву оператора и совпадает с метриками движка на тех же данных.
- Работа полностью офлайн: шрифты, ECharts и шаблоны в образах, внешних обращений нет.
- `just lint`, `just test`, `just e2e` и CI зелёные; замеры импорта 20 000 строк и печати графика крупного подразделения — в `docs/benchmarks/`.

## Что не входит

- Миграция данных из legacy (open-questions №19) — отдельной задачей, не в этой фазе.
- Произвольный конструктор отчётов: формы фиксированы, расширяемы только шаблоны.
- Удаление через импорт (вопрос 55).
- Фоновая печать больших пакетов документов — только если замеры покажут необходимость.
