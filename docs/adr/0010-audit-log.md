# 0010. Журнал аудита

## Статус
Принято (2026-09-26)

## Контекст

`CLAUDE.md`: каждое изменение данных попадает в журнал аудита — кто, что, когда, было → стало. Ряд операций требует обязательного комментария и должен быть виден отдельно: выдача допуска вопреки требованиям роли (ADR-0009), ручное нарушение отдыха (ADR-0008). Перевод человека в другое подразделение отдельной историей не хранится, поэтому его след есть только в аудите (`docs/open-questions.md` №24).

Ответ заказчика (№28): журнал хранится в каждом сервисе, оператор видит историю изменений в своём scope, администратор — весь журнал.

## Варианты

1. **Таблица `audit_log` в каждом сервисе, запись в той же транзакции, что и изменение.** Сводный просмотр строится в `analytics` из событий.
   - Плюсы: запись аудита атомарна с изменением, потерять её нельзя; сервис не зависит от доступности другого сервиса; правило «не ходить в чужие БД» соблюдается.
   - Минусы: сводный журнал в `analytics` появляется с задержкой (eventual consistency).
2. **Отдельный сервис аудита**, куда сервисы отправляют записи по HTTP или через события.
   - Минусы: при недоступности сервиса аудита приходится либо блокировать изменения, либо терять записи; ещё один сервис сверх целевой схемы `CLAUDE.md`.
3. **Триггеры PostgreSQL**, пишущие было/стало.
   - Плюсы: невозможно забыть записать.
   - Минусы: триггер не знает оператора, комментарий и `request_id`; бизнес-действие (`clearance.grant_override`) превращается в набор низкоуровневых UPDATE.

## Решение

**Вариант 1.** `libs/common` даёт один механизм: сервисный слой вызывает `audit.record(action, entity, before, after, comment)` внутри транзакции. Контекст оператора (`actor_id`, `actor_unit_id`, `request_id`) берётся из запроса автоматически. Та же транзакция кладёт в `outbox` событие `audit.recorded`, из которого `analytics` строит сводный `audit_view`.

- Пишутся только изменённые поля (`before`/`after` — diff), а не целые объекты.
- `scope_unit_id` — подразделение, к которому относится запись. По нему журнал фильтруется той же scope-политикой, что и данные.
- Роль БД сервиса имеет на `audit_log` только INSERT и SELECT.
- Override-операции (`clearance.grant_override`, `assignment.rest_override`) без комментария отклоняются валидацией.

## Реализация (фаза 7b)

- Событие `audit.recorded` несёт также `service`, `occurred_at` и `actor_unit_id`.
- Сводный журнал `audit_view` живёт в `analytics`. Для начального заполнения и восстановления каждый сервис отдаёт свой журнал через `GET /internal/audit`.
- Покрытие проверяется тестом (`dutyflow_common.testing.audit_coverage`): во время полного прогона тестов сервиса каждый изменяющий маршрут из OpenAPI должен быть успешно вызван и хотя бы раз записать аудит. Исключения задаются явно, с причиной.

## Последствия

- Журнал читают все роли в пределах своего поддерева, включая наблюдателя (`viewer`): история изменений — часть просмотра данных (уточнено 2026-09-26, фаза 2a). Записи справочников без подразделения видит только суперадминистратор.
- Каждый сервис отдаёт `GET /audit?entity_type=&entity_id=` (история конкретного объекта — быстро, из своей БД). Сводный журнал по поддереву — `GET /api/analytics/audit`.
- `auth-admin` получает маленькую БД только под `audit_log`, потому что операции с операторами тоже аудируются.
- Объём до 5–10 млн записей в год (`docs/data-model.md` §8): в фазе 7 вводится партиционирование по месяцам и политика хранения.
- Тест-требование: каждая мутирующая ручка API покрыта проверкой, что создаётся запись аудита (общий pytest-фикстурный хелпер в `libs/common`).
