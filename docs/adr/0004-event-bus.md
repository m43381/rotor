# 0004. Шина событий: Redis Streams vs RabbitMQ/NATS

## Статус
Принято

## Контекст

Сервисы обмениваются доменными событиями (`unit.moved`, `person.updated`, `clearance.revoked`, `schedule.published`, `day_plan.accepted`, …) для поддержания консистентности read-model (`analytics`) и инвалидации локальных срезов (`scheduling` кэширует id/имена подразделений и людей, полученные батчами, и должен узнавать об их изменении). Также нужна очередь фоновых задач для `allocation` (долгие CP-SAT прогоны) и `documents` (импорт/печать). Требование изоляции: без внешних зависимостей, всё в docker compose офлайн.

Redis уже выбран в `CLAUDE.md` как компонент (Streams для событий, `arq` для фоновых задач) — этот ADR фиксирует и обосновывает этот выбор против альтернатив, а не открывает вопрос заново.

## Варианты

1. **Redis Streams + arq.** Consumer groups с at-least-once доставкой, `XPENDING`/`XCLAIM` для обработки зависших сообщений, `XADD ... MAXLEN ~` для ограничения роста. `arq` — Python-нативная очередь задач поверх Redis, использует тот же Redis instance.
   - Плюсы: один компонент инфраструктуры вместо двух (шина + очередь задач); Redis уже нужен как быстрый кэш/rate-limit слой в любом случае; простая офлайн-поставка (один образ); consumer groups покрывают наши сценарии (один читатель на группу, at-least-once, идемпотентные обработчики через `event_id`).
   - Минусы: нет встроенной маршрутизации по topic-паттернам (как у NATS subjects) или exchange/routing keys (как у RabbitMQ) — при необходимости сложной маршрутизации пришлось бы городить это в коде; persistence зависит от конфигурации Redis (AOF/RDB) — требует явной настройки для durability на уровне "не потерять событие при рестарте".
2. **RabbitMQ.** Зрелая AMQP-шина, гибкая маршрутизация (exchanges/routing keys), устойчивая persistence "из коробки", DLQ как встроенный паттерн.
   - Минусы: ещё один компонент инфраструктуры (Erlang VM) в дополнение к Redis, который всё равно нужен под кэш/rate-limit; сложнее эксплуатационно для дипломного/пилотного масштаба.
3. **NATS (JetStream).** Легковесный, быстрый, хорошая история для микросервисов.
   - Минусы: тоже отдельный компонент; JetStream persistence и семантика consumer groups менее знакомы команде из одного разработчика (дипломника) по сравнению с Redis, который уже используется как кэш.

## Решение

**Redis Streams** для доменных событий + **arq** для фоновых задач, на одном Redis instance. Мотивация — минимизация числа инфраструктурных компонентов при офлайн-поставке (правило: "никаких внешних обращений", каждый лишний компонент — это лишний образ, лишняя точка отказа и лишняя вещь для сертификации на закрытом контуре), при том что наши сценарии обмена событиями простые (публикация в один stream на тип события, один consumer group на потребителя) и не требуют богатой маршрутизации RabbitMQ/NATS.

Требования к надёжности:
- `XADD` — часть той же транзакции через **transactional outbox** (см. `docs/architecture.md` §5): запись домена и запись в outbox-таблицу — одна DB-транзакция; отдельный релей-процесс читает outbox и делает `XADD`, помечая как отправленное — так публикация в Redis не теряется при падении между записью в БД и публикацией.
- Redis настраивается с AOF (`appendonly yes`) в `deploy/` для персистентности между рестартами контейнера.
- Все консьюмеры идемпотentны по `event_id` (дедупликация на своей стороне) — Streams даёт at-least-once, не exactly-once.

## Уточнение (фаза 7d): рост потоков

Сначала рост ограничивался через `XADD ... MAXLEN ~100000`. Нагрузочный прогон показал, что при массовых операциях это теряет события. Массовая выдача 713 тыс. допусков дала столько же событий `clearance` и `audit`. Консьюмер отстал больше чем на 100 тыс. событий, и Redis удалил ещё не прочитанные записи. Консьюмер подтвердил пустые сообщения, и в сводный журнал попало 278 тыс. записей аудита personnel из 770 тыс.

Теперь `XADD` вызывается без ограничения. Релей раз в минуту обрезает потоки точным `XTRIM MINID` (`dutyflow_common.streams`) и удаляет только записи, для которых выполнены оба условия:
- запись старше трёх суток — это срок, в течение которого новая группа консьюмеров может прочитать историю;
- запись подтверждена всеми группами: она раньше самой старой неподтверждённой и не дальше последней выданной.

Если консьюмер стоит, поток растёт. Это видно в `doctor` по отставанию, а памяти Redis на эталонной машине хватает на миллионы событий.

## Последствия

- Один образ Redis обслуживает и события, и очередь фоновых задач `allocation`/`documents` — меньше поверхность для офлайн-сборки.
- Если в будущем понадобится сложная маршрутизация (много типов подписчиков на пересекающиеся подмножества событий, приоритеты, DLQ с ретраями по расписанию) — это повод для пересмотра ADR в пользу RabbitMQ; на старте это не требуется.
- outbox-таблица есть в каждом сервисе-продюсере (`org`, `personnel`, `scheduling`) — небольшой, но обязательный шаблонный код, вынесенный в `libs/common`.
