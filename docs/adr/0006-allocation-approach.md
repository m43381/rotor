# 0006. Подход к алгоритму распределения

## Статус
Принято (детальный дизайн — `docs/allocation-design.md`)

## Контекст

Legacy использовал единый жадный алгоритм и для распределения ячеек между подразделениями (`PlanAutomationService`), и для назначения людей (`AssignmentAutomationService`) — с O(1) выбором "лучшего следующего" кандидата на каждом шаге, без возможности пересмотреть решение, без учёта состава наряда по ролям, без жёстких ограничений на отдых, со справедливостью только внутри календарного месяца (полный разбор — `docs/legacy-analysis.md` §2.4–2.5, §4). При этом сам жадный алгоритм на реальных объёмах (учебное заведение, тысячи людей) работал приемлемо по времени — проблема не в скорости, а в качестве решения и в отсутствии объяснимости/детерминизма гарантий.

Целевые НФТ: распределение на месяц для крупного подразделения — секунды; до 50 тыс. личного состава; детерминизм (seed); движок как чистая функция, не зависящая от БД (ADR-0001).

## Варианты

1. **Оставить единый жадный алгоритм**, просто исправить N+1 (векторизовать капасити/пенальти запросы). Дёшево, но не решает: недокомплект к концу месяца из-за порядка обработки дат, отсутствие оптимальности даже локально на подзадачах, где точный алгоритм посчитался бы быстро (один день, венгерский алгоритм — O(n³) на малом n тривиален).
2. **Единый точный решатель на всю задачу целиком** (например, один большой CP-SAT или LP на весь месяц × всё дерево × всех людей). Даёт глобальный оптимум, но: не масштабируется на 50 тыс. человек (число переменных = люди × дни × роли — миллионы, решатель не уложится в секунды); не соответствует реальному процессу (подразделения физически делегируют и решают локально, а не одним центральным штабом).
3. **Многоуровневая воронка**: иерархическая декомпозиция по дереву → дешёвые векторные фильтры допустимости → векторная проверка ёмкости/дефицитов → векторный скоринг → метод оптимизации, выбираемый по размеру подзадачи (пропорциональное представительство + min-cost flow для распределения по подразделениям; MRV-жадный + локальный поиск для больших подзадач; венгерский алгоритм/min-cost flow для одного дня; OR-Tools CP-SAT для месяца внутри одного подразделения до ~200–300 человек).

## Решение

**Многоуровневая воронка** (детально — `docs/allocation-design.md`). Обоснование выбора именно этой архитектуры, а не варианта 1 или 2:

- Она **повторяет структуру реального процесса**: верхнее подразделение делегирует вниз, каждое подразделение внутри себя решает свою подзадачу — иерархическая декомпозиция (уровень 0) не искусственна, а буквально то, что уже делает `scheduling` через workflow делегирования (унаследованный из legacy паттерн, см. `docs/legacy-analysis.md` §5). Это одновременно и архитектурное, и алгоритмическое решение.
- Она **делает задачу на каждом уровне маленькой** — после декомпозиции по дереву самая крупная подзадача точного решателя (CP-SAT) — это один месяц внутри одного подразделения (до нескольких сотен человек), что укладывается в секунды. Глобальный точный решатель (вариант 2) на всю организацию не нужен и не уложился бы в НФТ.
- Она **соответствует известным асимптотикам** на каждом уровне (см. `docs/allocation-design.md` за обоснованием каждого пункта): O(P·K) для допустимости (векторно, без циклов на Python — устраняет главный класс проблем legacy, N+1 на `_calculate_capacity`/`_recent_penalty`), O(K·T·P) для ёмкости одним матричным умножением, O(n³) для одного дня (венгерский алгоритм — точный оптимум на малом n), полиномиальные эвристики (MRV + локальный поиск) для больших подзадач без точного решателя, CP-SAT с таймаутом и greedy-хинтом для среднего масштаба.
- Она даёт **естественные точки для объяснимости**: на каждом уровне воронки уже есть проверенная причина отсева (нет допуска → не прошёл уровень 1; недостаточная ёмкость → уровень 2 объясняет дефицит человеческим языком; проигрыш в скоринге → уровень 3 хранит полный вектор признаков) — то, что в legacy было зачаточным (top-5 кандидатов в preview-ответе, не сохранённым в БД), в новой архитектуре встроено по конструкции.
- Экспоненциально затухающая нагрузка (уровень 3) и перенос долга между периодами (уровень 4, квоты по ёмкости с учётом долга) напрямую устраняют проблему legacy "справедливость только внутри календарного месяца" (`docs/legacy-analysis.md` §4.5).

**Отклонено:**
- Вариант 1 (патч жадного алгоритма) — не решает структурные проблемы качества решения (жадность по датам, отсутствие ролей/жёстких ограничений отдыха), только производительность; для диплома также не даёт материала для сравнения подходов.
- Вариант 2 (единый точный решатель) — не проходит по НФТ на масштабе 50 тыс. человек и не соответствует организационной реальности делегирования.

## Последствия

- Движок значительно сложнее в реализации и тестировании, чем один жадный проход — требует дизайн-документа (`docs/allocation-design.md`), бенчмарк-стенда (`tools/bench`) и генератора синтетических данных (`tools/`) как отдельных артефактов, что и заложено в `docs/roadmap.md`.
- Экспериментальная часть (сравнение legacy-жадного baseline против MRV+LS/Hungarian/CP-SAT на 1k/5k/20k/50k синтетических данных) становится центральной частью пояснительной записки — обоснование каждого уровня воронки уже написано с прицелом на использование в тексте диплома.
- Точный состав весов уровня 3 (скоринг) и жёстких/мягких ограничений уровня 4 (CP-SAT) требует конфигурации, которая живёт вне кода (в отличие от захардкоженных констант legacy) — обязательное требование к реализации, не опция.
