# 0002. Аутентификация и авторизация: Keycloak vs собственный auth-сервис

## Статус
Принято (2026-09-26). Ранее было «предварительно», решение ждало ответа о целевой ОС и сертификации. Ответ (`docs/open-questions.md` №17): требования к отечественной ОС и сертификации пока неизвестны, целевая платформа — обычный Linux + Docker, Keycloak подтверждён.

## Контекст

Единственный вид пользователя системы — оператор, привязан к подразделению, видит данные в пределах scope (своё подразделение / дети / поддерево / всё). Самостоятельной регистрации нет — операторов создаёт администратор. До 5 000 учётных записей. Работа полностью офлайн, без доступа в интернет.

Legacy использовал Django `auth.User` + `UserProfile` (1–1, с `unit`) и полностью самописную сессионную аутентификацию — рабочую, но: нет OIDC/JWT, нет готового admin UI для управления пользователями отдельно от основного приложения, MFA/password-policy пришлось бы писать самим.

## Варианты

1. **Keycloak** (self-hosted, офлайн-совместим) как IdP: OIDC/JWT, грубые роли (`superadmin`, `unit_admin`, `operator`, `viewer`), `unit_id` как custom claim в токене. Тонкая авторизация (scope по дереву, поля/списки/меню) — не в Keycloak, а в `libs/common`.
2. **Собственный auth-сервис на FastAPI** — хранит пользователей/пароли/сессии сам, выдаёт свои JWT.
3. **OPA (Open Policy Agent)** как отдельный сервис/sidecar для *авторизации* (не аутентификации) — рассмотрен отдельно от выбора IdP, см. ниже.

## Решение

**Keycloak** для аутентификации и грубых ролей + `unit_id` в JWT. Тонкая авторизация (роль × ресурс × действие × scope по поддереву, plus поля/списки/меню — обобщение `access_control` из legacy) — в `libs/common`, используется каждым сервисом при валидации JWT и построении SQL-предикатов по `ltree`.

Причины:
- OIDC/JWT "из коробки": refresh-токены, revoke, password policy, брутфорс-защита — не изобретаем заново то, что имеет известные проблемы безопасности при самописной реализации.
- Admin REST API Keycloak закрывает потребность "администратор создаёт операторов из UI" — `auth-admin` (тонкий FastAPI) становится удобной обёрткой поверх него, а не полноценным identity-сервисом.
- Keycloak одним образом ставится в docker compose и работает полностью офлайн (нет обязательных внешних вызовов) — совместимо с требованием изоляции.
- Тонкая scope-модель специфична для домена (дерево подразделений через `ltree`) — её проще и быстрее выразить как SQL-предикаты в общей библиотеке, чем городить дополнительный сервис (OPA) с sidecar-архитектурой ради него: у нас один язык (Python) на все сервисы, Rego добавил бы второй язык политик без выигрыша в скорости или ясности.

**Отклонено:**
- Собственный auth-сервис — экономит один компонент (Java/Keycloak), но перекладывает на нас ответственность за безопасность хранения паролей, токенов и их жизненного цикла; для диплома это не даёт архитектурной ценности, а риск выше.
- OPA — оправдан при многоязычном ландшафте сервисов или при необходимости централизованного аудита политик независимо от кода; здесь все сервисы на Python и делят `libs/common`, так что выделенный сервис политик добавляет сетевой вызов на каждую проверку без выигрыша в выразительности.

## Последствия

- Realm-экспорт Keycloak версионируется в `deploy/keycloak/` и накатывается при `docker compose up` (детерминированная офлайн-поставка).
- `libs/common` становится точкой единственной правды для scope-предикатов — все сервисы обязаны использовать её, а не писать свою фильтрацию по дереву (иначе повторится проблема "двух систем прав" из legacy, см. `docs/legacy-analysis.md` §3).
- Сервисы зависят не от Keycloak, а от стандартного OIDC/JWT: `libs/common` проверяет подпись по JWKS, `issuer` и имена claim-ов (`unit_id`, роли) берутся из конфигурации. Поэтому IdP можно заменить (например, на ALD Pro или другое сертифицированное СЗИ, если появятся требования Astra Linux/ФСТЭК), не трогая бизнес-сервисы; изменится только `auth-admin`. Такая замена оформляется отдельным ADR-пересмотром.
- `auth-admin` не хранит собственных пользователей — только вызывает Keycloak Admin API, что упрощает его до тонкого прокси с валидацией и аудитом.
