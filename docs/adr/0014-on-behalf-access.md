# 0014. Доступ `documents` к данным других сервисов — от имени оператора

## Статус
Принято (2026-09-27, план фазы 6, шаг 6a)

## Контекст

`documents` импортирует личный состав, допуски и освобождения в `personnel` и печатает формы по данным `scheduling`, `personnel` и `org` (фаза 6). Каждый раз это действие конкретного оператора: импорт в его подразделения, печать его графика. Сервисы не ходят в чужие БД (ADR-0001), значит `documents` работает через API владельцев. Вопрос — с какими правами.

## Варианты

1. **Внутренние batch-эндпоинты со служебным токеном** (`/internal/*`, как `scheduling` → `personnel` для снимка).
   - Плюсы: привычный путь, не зависит от срока жизни токена оператора.
   - Минусы: `documents` должен сам проверять scope оператора — то есть держать копию политики и проекцию дерева чужого домена. В журнале аудита владельца изменения записаны на служебную учётную запись, а реальный оператор теряется или передаётся «на честном слове». Для записи (импорта) внутренний путь в обход политики опасен.
2. **Публичный API владельца от имени оператора (on-behalf-of).** `documents` передаёт дальше токен оператора из запроса.
   - Плюсы: права, проверки и аудит — ровно те же, что при работе из интерфейса; копии политики нет; в журнале — реальный оператор.
   - Минусы: запрос ограничен сроком жизни токена (минуты) — долгие операции так не выполнить; публичный API владельца должен уметь пакетные операции.
3. **Обмен токена (OAuth 2.0 Token Exchange) в Keycloak.**
   - Плюсы: `documents` получает собственный токен «от имени» с нужной аудиторией.
   - Минусы: дополнительная настройка Keycloak и ещё один вызов на каждую операцию; при одной аудитории `dutyflow-api` у всех сервисов выигрыша нет.

## Решение

**Вариант 2.**
- Клиент `dutyflow_common.upstream.UpstreamClient` передаёт `Authorization` оператора и `X-Request-Id`.
  - Ошибки владельца (4xx) доходят до оператора без изменений — с тем же кодом и текстом.
  - Недоступность (сеть, 5xx) — 503.
  - Повторяются только чтения: запись могла уже пройти.
- Пакетные операции живут в публичном API владельца. Первая — `POST /imports/{kind}` в `personnel`: проверка (`dry_run`) и применение с хэшем предпросмотра. Права проверяются по каждой строке, как у одиночных операций.
- Своя БД `documents` хранит только служебное: задачи импорта с файлами (удаляются через 7 дней), позже — настройки и шаблоны документов.
- Долгих операций от имени оператора нет. 20 000 строк проверяются за 1 с и применяются за 13 с (`docs/benchmarks/import.md`), это в пределах срока жизни токена. Если понадобятся фоновые задачи (например, пакетная печать), их выполнит воркер со служебным токеном и явной записью инициатора — отдельным решением.

## Последствия

- `documents` не зависит от политики доступа чужих доменов: изменения правил в `personnel` сразу действуют и на импорт.
- `analytics` строит собственную read-model по событиям и проверяет scope сам (общая политика и проекция подразделений, ADR-0011). Это не противоречит решению: у аналитики свои данные, а не чужие.
- Внутренние `/internal/*` остаются для служебных сценариев без оператора: снимок задачи, синхронизация проекций.
