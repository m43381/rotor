# 0021. Работа по HTTP и установка из репозитория

## Статус
Принято (2026-10-01). Заменяет часть ADR-0017 про HTTPS; поставка, копии и проверки из ADR-0017 остаются в силе. Пересматривает open-questions №60 (№72).

## Контекст

Стенд разворачивается на сервере заказчика в локальной сети. Код копируется с GitHub, запуск — `docker compose up`. Заказчик требует:
- работать по обычному HTTP, без сертификатов и их установки на рабочие места;
- менять внешний порт правкой конфигурации: на сервере порт может быть занят.

До этого (ADR-0017) шлюз принимал HTTPS на сертификате внутреннего УЦ, а адрес стенда (`PUBLIC_URL`) и порт задавались в `.env` отдельно. При смене порта их нужно было менять согласованно.

У HTTP есть техническое препятствие. Вход идёт через Keycloak по OIDC Authorization Code + PKCE, и `oidc-client-ts` считает `code_challenge` через `crypto.subtle.digest`. Браузер даёт `crypto.subtle` только в защищённом контексте (HTTPS или `localhost`), поэтому по `http://<IP сервера>` вход падает с ошибкой.

## Варианты

### Протокол
1. Оставить HTTPS по умолчанию, HTTP сделать настройкой.
   - Минусы: два варианта конфигурации шлюза и Keycloak, которые нужно поддерживать и проверять; заказчику нужен только один.
2. **Только HTTP.**
   - Плюсы: проще установка, нет сертификатов и их продления, на рабочих местах ничего не настраивается.
   - Минусы: пароли и токены передаются по сети открытым текстом. Это приемлемо только в доверенной изолированной сети.

### PKCE без `crypto.subtle`
1. Отключить PKCE в клиенте SPA и в Keycloak.
   - Минус: публичный клиент без PKCE слабее защищён от перехвата кода авторизации.
2. **Своя реализация SHA-256**, которая подставляется в `crypto.subtle.digest`, только если браузер его не дал.
   - Плюсы: PKCE S256 и настройки Keycloak не меняются; на HTTPS и `localhost` работает штатная реализация браузера. Около 70 строк кода без зависимостей, проверено тестом против эталона.

### Адрес и порт
1. Отдельные `PUBLIC_URL` и порт, как раньше.
2. **`SERVER_HOST` и `GATEWAY_PORT`, а `PUBLIC_URL=http://${SERVER_HOST}:${GATEWAY_PORT}`.** Подстановку выполняет docker compose при чтении `.env`; `dutyflow.sh` и `tools/gen` раскрывают её так же.

## Решение

**Только HTTP, своя SHA-256 для PKCE, адрес собирается из имени сервера и порта.**

- Шлюз nginx слушает только порт 80 контейнера, наружу пробрасывается `GATEWAY_PORT`. Перенаправления на HTTPS и HSTS нет.
- Keycloak: `sslRequired: none` в realm-файле и в `keycloak-init`, чтобы действовало и на уже созданном realm. Значение `external` пускало бы по HTTP только с частных адресов.
- Сертификаты, контейнер их выпуска и команда `dutyflow.sh certs` убраны. Модуль `dutyflow_common.certs` остаётся: `doctor` проверяет сертификат, если задан `CERTS_DIR`.
- Установка из репозитория: `./dutyflow.sh init` (только `.env` со случайными паролями, без Python на хосте), затем `docker compose up -d --build` в `deploy/`.

## Последствия

- Смена порта: правка `GATEWAY_PORT` и `docker compose up -d`. Адрес Keycloak (`KC_HOSTNAME`), издатель токенов, адреса возврата клиента SPA (`keycloak-init`) следуют за `PUBLIC_URL`. Для порта 80 `PUBLIC_URL` указывается без порта, потому что браузер не пишет `:80` в адресе, а Keycloak сравнивает адреса как строки.
- Браузер, который раньше открывал стенд по HTTPS, мог запомнить HSTS для этого имени и сам переходить на `https://`. Нужно очистить HSTS для адреса (описано в `deploy/README.md`).
- Защита канала — задача сети заказчика. Если HTTPS понадобится, его можно вернуть терминирующим прокси перед шлюзом без изменений в сервисах: заголовки `X-Forwarded-*` уже передаются.
