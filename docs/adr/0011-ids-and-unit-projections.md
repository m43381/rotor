# 0011. Идентификаторы и локальные проекции дерева подразделений

## Статус
Принято (2026-09-26)

## Контекст

1. Сущности ссылаются друг на друга через границы сервисов (`person.unit_id`, `clearance.duty_role_id`, `assignment.person_id`) без FK. Нужен формат идентификаторов, который генерируется где угодно и не конфликтует.
2. Почти каждый список фильтруется по scope оператора — по поддереву подразделений (ADR-0003). Дерево и `ltree`-путь принадлежат `org`. Если `personnel` и `scheduling` на каждый запрос списка будут спрашивать у `org` «все потомки узла X», то каждый запрос оператора превратится в межсервисный вызов, а JOIN по поддереву в SQL станет невозможен.

## Варианты

### Идентификаторы
1. `bigint identity` в каждом сервисе — компактно, но id генерирует только БД владельца (сложнее превью импорта и идемпотентные повторы запросов), а числа разных сущностей легко перепутать.
2. **UUIDv7** — генерируется в приложении, упорядочен по времени (B-tree-индексы не фрагментируются, как с UUIDv4), уникален глобально.

### Scope в чужих сервисах
1. Запрашивать у `org` список `unit_id` поддерева на каждый запрос и подставлять в `WHERE unit_id = ANY(:ids)`.
   - Минусы: сетевой вызов на каждый список; для оператора верхнего уровня — тысячи id в запросе.
2. **Локальная read-only проекция `unit_projection(unit_id, path)`** в каждом сервисе, где нужен scope, поддерживаемая событиями `unit.created/moved/deleted` (ADR-0004).
   - Плюсы: scope — индексный JOIN `path <@ :scope_path` в своей БД, без сети.
   - Минусы: задержка между изменением дерева и обновлением проекции (секунды); нужен механизм начального наполнения и пересинхронизации.

## Решение

- **UUIDv7** для всех сущностей, генерируется в приложении (`libs/common`).
- **`unit_projection`** в `personnel`, `scheduling`, `analytics`. Это не нарушение правила «сервисы не ходят в чужие БД»: данные приходят через события и batch-API `org`, проекция — собственная таблица сервиса, только для чтения. Владельцем дерева остаётся `org`.
- При старте сервиса, если проекция пуста или отстала (сравнение `last_event_id`), выполняется полная пересинхронизация через `POST /internal/units/batch`.
- `path` в `org` строится из неизменяемого числового `node_no`, а не из имени, поэтому переименование не меняет путей. Перемещение узла порождает `unit.moved` с новым путём, и проекции обновляют поддерево одним UPDATE.

## Последствия

- Уточняет ADR-0003 («другие сервисы хранят только `unit_id`»): кроме `unit_id` они хранят проекцию дерева для scope-фильтрации.
- Кратковременное расхождение после перемещения подразделения допустимо для чтения. Для записи (например, проверки права выдать допуск) сервис может дополнительно сверить путь через `org`, если событие ещё не обработано — решается при реализации политики доступа.
- Тест: интеграционный сценарий «переместили поддерево → оператор нового родителя видит людей» с ожиданием обработки события.
