# 0001. Микросервисы и их границы

## Статус
Принято

## Контекст

DutyFlow 2 — новый продукт с нуля, заменяющий Django-монолит (~11 тыс. строк, см. `docs/legacy-analysis.md`). Монолит смешивал в одних Django-приложениях: справочники (подразделения/звания/типы нарядов), личный состав, планирование/делегирование, назначение людей и права доступа — что затрудняло independent-развитие движка распределения (самой сложной и требовательной к производительности части) отдельно от CRUD-частей.

Нефункциональные требования: до 5 000 операторов, 20–50 тыс. личного состава, распределение на месяц для крупного подразделения — за секунды, полная сетевая изоляция, docker compose как способ поставки.

## Варианты

1. **Модульный монолит** (один Python-процесс, чёткие внутренние границы модулей). Проще в разработке и деплое, но: движок распределения (CPU-bound, numpy/OR-Tools) и CRUD-сервисы масштабируются по-разному; сложнее держать чистую границу "движок = чистая функция" без соблазна дёрнуть ORM напрямую; хуже для диплома с точки зрения демонстрации архитектурных решений.
2. **Микросервисы по доменным границам** (предложенная в `CLAUDE.md` схема: `gateway`, `auth`, `org`, `personnel`, `scheduling`, `allocation`, `analytics`, `documents`).
3. **Микросервисы по техническим слоям** (например, отдельно "API-сервис", "воркер-сервис", "сервис отчётов" без привязки к домену) — отклонено: такие границы приводят к тому, что одна доменная транзакция размазывается по сервисам без явного владельца данных.

## Решение

Микросервисы по доменным границам, как в `CLAUDE.md`, с явным дополнительным принципом: **`allocation` не имеет собственной предметной БД** и является границей "чистая функция + воркер", а не CRUD-сервисом. `scheduling` — единственный владелец рабочих данных планирования (графики/планы/назначения/pin), `allocation` только считает и возвращает решение.

Каждый сервис — отдельная БД (см. правило #5 в `CLAUDE.md`: сервисы не ходят в чужие БД). Взаимодействие — HTTP batch-эндпоинты для синхронных запросов и события через outbox для асинхронной консистентности.

Границы **не дробить сильнее** без нового ADR — в частности, не выделять `scheduling`/`allocation` в более мелкие сервисы, пока бенчмарки не покажут необходимость.

## Последствия

- Каждый сервис можно тестировать, деплоить и (для `allocation`) бенчмаркать независимо.
- Явная граница делает возможным требование CLAUDE.md #6 (движок детерминирован, не зависит от БД).
- Cтоимость: больше инфраструктурного кода (batch-эндпоинты, outbox, событийная согласованность) по сравнению с монолитом — оправдано целями диплома (демонстрация архитектуры) и разной нагрузочной природой `allocation` vs остальных сервисов.
- Локальная разработка требует `docker compose` с 8+ сервисами + Postgres + Redis + Keycloak — заложено в `CLAUDE.md` как целевой способ запуска.
