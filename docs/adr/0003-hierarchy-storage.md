# 0003. Хранение иерархии подразделений

## Статус
Принято (замеры производительности запланированы на фазу 1 «ходячий скелет», см. `docs/roadmap.md` — числа будут добавлены сюда после реализации `org`)

## Контекст

`Unit` — дерево произвольной глубины (академия → факультет → кафедра → …), до нескольких тысяч узлов. Почти все операции системы фильтруются по scope, выражаемому через поддерево: "моё подразделение", "прямые дети", "весь мой поддерево". Legacy хранил дерево как adjacency list (`parent` FK) и вычислял descendants **рекурсией в Python с одним SQL-запросом на узел** (`Unit.get_descendants_ids`) — подтверждённый в `docs/legacy-analysis.md` hot-path баг: это выполняется на **каждый HTTP-запрос** оператора верхнего уровня через `AccessContext`.

Это первое и самое важное архитектурное решение, которое нужно исправить относительно legacy.

## Варианты

1. **Adjacency list + рекурсивный CTE** (`WITH RECURSIVE`). Данные хранятся как в legacy (`parent_id`), но обход дерева делается одним SQL-запросом на стороне БД, а не в Python.
   - Плюсы: минимальные изменения схемы, знакомо любому разработчику на SQL, вставка/перемещение узла — тривиальны (один `UPDATE parent_id`).
   - Минусы: рекурсивный CTE на каждый scope-запрос — это по-прежнему логарифмически/линейно растущая работа на стороне БД на каждый доступ; сложнее строить составные индексы "принадлежит поддереву X" для JOIN с другими таблицами (`Person`, `DayPlan`) без денормализации.
2. **`ltree`** (расширение PostgreSQL). Каждый узел хранит материализованный путь (`academy.faculty3.dept12`), поддерево — один индексный предикат `path <@ 'academy.faculty3'`, есть GiST/B-tree индексы под это.
   - Плюсы: один индексный предикат вместо рекурсии — тривиально JOIN'ится с `Person`/`DayPlan` по scope; O(log n) через индекс на операции "принадлежит поддереву"; библиотека зрелая, включена в стандартную поставку PostgreSQL (не требует стороннего расширения кроме `CREATE EXTENSION ltree`, что совместимо с офлайн-поставкой — в образ уже входит).
   - Минусы: перемещение поддерева требует обновления `path` у всех потомков (одним `UPDATE ... WHERE path <@ old_path` — не рекурсия, но при глубокой реорганизации задевает много строк); путь ограничен длиной label'а (не проблема при разумной длине slug'ов уровней).
3. **Closure table** (таблица всех пар предок-потомок). Максимально гибкие запросы (быстрый поиск и предков, и потомков, и произвольных срезов), но O(n²) по объёму в худшем случае для широких деревьев и требует поддерживать отдельную таблицу синхронно при каждой вставке/перемещении (лишний источник рассинхронизации, лишняя сложность в `org`).

## Решение

**`ltree`** как основное представление дерева в `org`. `Unit.path ltree`, GiST-индекс на `path`. Все scope-предикаты (`own_unit`, `children`, `own_and_children`, `all_descendants`, `own_and_all_descendants`, `all` — те же 7 видов scope, что в legacy `access_control`, см. `docs/legacy-analysis.md` §3) транслируются в `libs/common` в условия по `ltree` (`path = X`, `path ~ 'X.*{1}'`, `path <@ X`, и т.д.), а не в рекурсивный Python-обход.

`parent_id` тоже хранится (для тривиальных FK-связей и целостности), `path` поддерживается синхронно при вставке/перемещении узла триггером или явно в сервисном слое `org` — perемещение поддерева уже не проблема на масштабах в тысячи подразделений (одна операция обновления path потомков, не миллионы записей).

Batch-эндпоинты `org` (`/internal/units/batch`, `/internal/units/descendants-batch`) возвращают уже посчитанный на стороне БД срез — устраняя источник N+1, использовавшийся в legacy и в `AccessContext`, и в `PlanAutomationService`.

**Отклонено:**
- Чистый adjacency + рекурсивный CTE — не даёт выигрыша в JOIN-выразительности со scope-фильтрами на других таблицах по сравнению с `ltree`, при этом не проще в реализации.
- Closure table — оверхед синхронизации не оправдан при ожидаемой глубине/ширине дерева (единицы–десятки тысяч узлов, не миллионы); `ltree` даёт сопоставимую скорость чтения при меньшей сложности записи.

## Последствия

- `org` — единственный владелец `path`; другие сервисы (`personnel`, `scheduling`) хранят `unit_id` (FK по значению, не по факту БД) и получают срез дерева через batch-API, не пересчитывая его сами. Для scope-фильтрации они держат локальную read-only проекцию `unit_projection(unit_id, path)`, обновляемую событиями (уточнено в ADR-0011).
- Метки `ltree` — неизменяемые числовые `node_no`, а не имена: переименование подразделения не меняет путей (ADR-0011).
- `libs/common` содержит единый транслятор scope → `ltree`-предикат, переиспользуемый всеми сервисами — устраняет разделение "два движка прав", отмеченное как проблема legacy.
- Требуется бенчмарк на синтетических данных (генератор из `tools/`, см. `docs/roadmap.md`) на деревьях 1k/5k/20k/50k людей и нескольких глубин — числа появятся здесь как ADR-приложение после фазы 1, до этого решение принято на основании известных характеристик `ltree` (не на пустом месте: материализованный путь + GiST — стандартный паттерн PostgreSQL для деревьев, задокументированный и предсказуемый по асимптотике).
