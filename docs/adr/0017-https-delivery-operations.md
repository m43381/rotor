# 0017. HTTPS на внутреннем УЦ, пакет поставки и эксплуатация

## Статус
Принято (2026-09-29, план фазы 7, шаг 7c). Уточняет ADR-0007. Часть про HTTPS заменена ADR-0021 (2026-10-01): стенд работает по HTTP; поставка, копии и проверки остаются в силе.

## Контекст

До фазы 7 стенд работал по HTTP и поднимался только из репозитория командой `just up`, которая собирает образы. Для сдачи системы нужно закрыть четыре задачи:
- **HTTPS в изолированной сети.** Публичного УЦ нет. По open-questions №60 используется свой УЦ через `just certs`, сертификат сервера действует 2 года, вместо своего можно подложить сертификат заказчика.
- **Поставка на сервер без интернета** (ADR-0007): только Docker, без Python, Node, just и реестров.
- **Резервные копии** всех БД, включая Keycloak (№63): ежедневно, хранение 14 дней, восстановление в пустой стенд.
- **Проверка стенда** после установки и в работе.

## Варианты

**Выпуск сертификатов:**
1. `openssl` в одноразовом контейнере — так предполагал план.
   - Минусы: конфигурация SAN и расширений в виде текстового шаблона, проверка срока — разбором вывода.
2. **Модуль `dutyflow_common.certs` на `cryptography`.** Библиотека уже есть в образах сервисов.
   - Плюсы: SAN, EKU и срок задаются кодом и покрыты тестами; тот же модуль проверяет срок для `doctor`.

**Инструменты эксплуатации:**
1. Отдельные `install.sh` и `update.sh` плюс рецепты `just` — так предполагал план.
   - Минусы: `just` на сервере нет, а логика в двух местах разойдётся.
2. **Один `dutyflow.sh`** (bash и Docker), одинаковый в `deploy/` репозитория и в корне пакета; рецепты `just` его вызывают. Проверки, которым нужна внутренняя сеть стенда (`/health`, Redis, срок сертификата), выполняет одноразовый контейнер из образа сервиса (профиль `ops` в compose).

**Резервные копии:**
1. Файловая копия тома PostgreSQL. Минусы: нужна остановка, копия привязана к версии PostgreSQL.
2. **`pg_dump -Fc` каждой БД** в одноразовом контейнере `ops-db` без остановки работы; восстановление — `pg_restore` в пересозданные БД.

## Решение

- **HTTPS.**
  - Шлюз слушает 443 с TLS 1.2/1.3 и заголовком HSTS, порт 80 только перенаправляет на `PUBLIC_URL`.
  - Корневой сертификат (10 лет) создаётся один раз и при продлении сохраняется, поэтому рабочие места не перенастраиваются. Сертификат сервера (2 года) выпускается на имена и IP из `TLS_HOSTS`.
  - Keycloak получает схему из `X-Forwarded-Proto`, поэтому cookie сессий идут с флагом `Secure`.
  - `keycloak-init` при каждом запуске приводит адреса возврата клиента SPA к `PUBLIC_URL`: смена адреса или переход на HTTPS не требуют правки realm вручную.
- **Пакет поставки** (`just bundle <версия>` → `dist/dutyflow-<версия>.tar`):
  - `images.tar.gz` — образы сервисов с тегом версии и сторонние образы;
  - compose без секций `build` и с `pull_policy: never`;
  - `.env.example` с `DUTYFLOW_VERSION`, конфигурация, `dutyflow.sh`, `README.md` (руководство администратора), `MANIFEST.sha256`.
  - Секретов в пакете нет: `.env` со случайными паролями и сертификаты создаются на месте. Каталоги версий разделены, данные (тома compose-проекта `dutyflow`) общие.
  - `update <старый каталог>` переносит настройки, делает копию, загружает образы и запускает стенд.
  - Откат — `restore` копии перед обновлением из каталога старой версии, чьи образы остаются загруженными.
- **Резервные копии.**
  - `backup` снимает все БД кластера, включая Keycloak и read-model аналитики. Перестраивать read-model дольше и сложнее, чем хранить её в копии, а сама она небольшая.
  - В копию входят `.env` и сертификаты: без них копию не поднять на другом сервере. Поэтому копия — секрет того же уровня, что и данные; шифрование обеспечивается средствами хоста (№63).
  - `restore` останавливает стенд, пересоздаёт БД через `db-init` и заливает дампы. Затем очищает Redis: события после точки копии к восстановленным данным не относятся, а неотправленное из outbox уходит заново, повторы отсекаются отметками обработки (ADR-0004).
- **Проверка** (`doctor`):
  - состояние контейнеров;
  - `/health` сервисов и готовность Keycloak;
  - отставание консьюмеров и DLQ;
  - срок сертификата;
  - свежесть копий и место на диске.
  - Код выхода 1 при проблемах, поэтому команду можно ставить в мониторинг.
  - У релеев и консьюмеров нет HTTP-порта: их живость проверяет healthcheck по файлу-пульсу (`dutyflow_common.heartbeat`), который обновляется после каждого успешного цикла.
- **Compose.**
  - Ротация json-логов: 5 файлов по 20 МБ на контейнер.
  - Предел памяти воркера распределения: `ALLOCATION_WORKER_MEMORY`, по умолчанию 4 ГБ.
  - `restart: unless-stopped` у всех долгоживущих сервисов.

## Отличия от плана фазы 7

- Сертификаты выпускает `cryptography`, а не `openssl`: см. «Варианты».
- В realm остаётся `sslRequired: external`, а не `all`. Сервисы обращаются к Keycloak внутри сети compose по HTTP (`keycloak:8080`: JWKS, Admin API), а снаружи он доступен только через шлюз по HTTPS. С `all` пришлось бы вести TLS и во внутренней сети, что для одного хоста избыточно.
- Вместо `install.sh`, `update.sh` и `MANIFEST.txt` — один `dutyflow.sh`, а также файлы `VERSION` и `MANIFEST.sha256`, который проверяется `sha256sum -c`.

## Последствия

- Проверено на машине разработчика:
  - установка из пакета в отдельный compose-проект после удаления образов версии из Docker, то есть только из `images.tar.gz`;
  - вход администратора по нестандартному адресу, включая перенаправление с HTTP;
  - обновление из соседнего каталога и откат восстановлением копии;
  - восстановление рабочего стенда из копии с последующим полным прогоном e2e (34 теста).
- Разработка тоже идёт по HTTPS (`https://localhost:8443`). Инструменты seed доверяют `deploy/certs/ca.crt`, e2e и скриншоты игнорируют ошибки сертификата.
- На Windows `curl` (schannel) не проверяет отзыв для УЦ без CRL — нужен ключ `--ssl-no-revoke`. Браузеры и Python это не затрагивает.
- Ежедневный запуск копии — задача хоста (cron, пример в `deploy/README.md`): отдельный планировщик в стенде не нужен.
