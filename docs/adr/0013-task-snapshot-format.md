# 0013. Формат снимка задачи распределения

## Статус
Принято (2026-09-27, план фазы 3, шаг 3c)

## Контекст

Движок распределения (`allocation`) — чистая функция «снимок → решение» (ADR-0006, `docs/architecture.md` §4). Снимок собирает `scheduling`: дерево, календарь, люди с допусками и освобождениями, ячейки, назначения и закрепления, лимиты, история нагрузки. Снимок сохраняется, чтобы воспроизвести прогон («почему поставили именно его») и прогонять бенчмарки без сервисов.

Бенчмарк фазы 2b (`docs/benchmarks/people-snapshot.md`) показал, что наивный JSON со списком людей, где каждый допуск повторяет UUID роли, весит 22 МБ на 50 тыс. человек, и около половины объёма — повторяющиеся UUID.

## Варианты

1. **JSON «как в API»** — объекты с UUID-ссылками.
   - Плюсы: читается глазами, отлаживать легко.
   - Минусы: объём и время сериализации растут из-за повторов UUID; движку всё равно нужно перекладывать всё в индексы numpy.
2. **JSON со словарями и индексами.** Подразделения, роли и люди — массивы; ссылки между ними — номера в этих массивах. UUID встречается один раз.
   - Плюсы: объём в разы меньше, индексы сразу годятся как номера строк и столбцов матриц `C[P, K]`, `A[P, T]` (`docs/allocation-design.md`); формат остаётся текстовым и переносимым.
   - Минусы: без словарей файл не читается, нужна версия формата.
3. **Apache Arrow / Parquet.**
   - Плюсы: колоночный формат, нулевое копирование в numpy.
   - Минусы: новая зависимость на обеих сторонах, двоичный формат сложнее отлаживать и хранить в тестах; выигрыш над вариантом 2 важен только на объёмах, которых в подзадаче подразделения нет (декомпозиция по дереву, уровень 0).

## Решение

**Вариант 2: JSON со словарями и индексами, версия формата `snapshot_version`.**

- Верхний уровень: `snapshot_version`, `hash` (SHA-256 содержимого без времени сборки — одинаковый вход даёт одинаковый hash, это нужно для детерминизма и `allocation_run.snapshot_hash`), `created_at`, `timezone`, `schedule`, `horizon`.
- `days` — все даты горизонта: хвост истории + месяц графика, с типом дня (`workday`, `weekend`, `holiday`, `preholiday`). Даты в остальных разделах — номера в этом массиве.
- `units` — поддерево подразделения графика (`id`, `parent`, `name`); `roles` — роли в ячейках со всем, что нужно для времени и нагрузки (`start_time`, `duration_minutes`, `rest_hours`, `load_weight`, `headcount`).
- `people` — у каждого номер подразделения, допуски `[роль, с, по]` (только к ролям из `roles`; границы — номера дней или `null`), освобождения `[с, по]`, разрешённый лимит `[всего, в выходные]` (правило уже выбрано при сборке, `docs/data-model.md` §5).
- `cells` — ячейки графиков поддерева за месяц: день, роль, подразделение графика, исполнитель, происхождение, статус делегирования, закрепление, родительская ячейка.
- `assignments` — назначения людей снимка за горизонт: id, человек, ячейка (или `null` для истории вне снимка), день, роль, тип наряда, интервал `t` в минутах местного времени от полуночи первого дня горизонта, отдых после наряда, занятые сутки, нагрузка, закрепление, признак автоматического назначения (движок пересматривает только свои), ручное нарушение. Интервал и отдых нужны, чтобы проверять отдых и для нарядов других ролей из истории (уточнено в фазе 4a до появления потребителей формата, версия осталась 1).
- Горизонт истории — 90 дней по умолчанию: хватает на хвост `max(duration) + max(rest_hours)` (ADR-0008) и окно затухания нагрузки (коэффициент подбирается в фазе 5).

**Отклонено:** вариант 1 — из-за объёма; вариант 3 — пока не нужен, к нему можно перейти в фазе 5, если бенчмарк покажет, что сериализация JSON стала узким местом. Смена формата — новая `snapshot_version`.

## Последствия

- Сборка снимка — один batch-запрос в personnel и по одному запросу в свою БД на каждый раздел, без N+1.
- Фиксированный порядок элементов (подразделения по пути, роли и люди по id, ячейки по дню и роли) делает `hash` воспроизводимым.
- Списки id длиннее лимита параметров asyncpg (32 767) передаются одним массивом (`dutyflow_common.db.in_array`) — найдено при подготовке снимка на 50 тыс. человек.
