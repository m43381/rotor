# 0005. Расширяемые характеристики личного состава

## Статус
Принято

## Контекст

`CLAUDE.md`: у личного состава — "расширяемые характеристики". Legacy вообще не имел этого понятия: `Person` — жёсткая схема (ФИО, `rank`, `unit`), допуски — отдельная таблица `DutyClearance` только к `DutyType` целиком (без ролей). Целевая система должна поддерживать требования к наряду **по ролям** (например, дежурный ×1, дневальный ×2), и требования к роли могут включать не только допуск, но и, потенциально, характеристики (например, "имеет категорию по вождению", "владеет языком", "рост/группа здоровья" — конкретный состав зависит от ответа на открытый вопрос в `docs/open-questions.md`). Схема должна поддерживать это, не зная заранее полный список возможных характеристик, и позволять фильтровать людей по ним векторно (см. `docs/allocation-design.md`, уровень 1: битовые маски/числовые векторы).

## Варианты

1. **EAV (Entity-Attribute-Value)** — отдельная таблица `(person_id, attribute_id, value)`. Максимально гибко, ничего заранее не типизировано.
   - Минусы: типизация значений размывается (числа/строки/даты в одном текстовом поле или множество value-колонок), запросы "у кого значение X больше Y" превращаются в JOIN на ту же таблицу много раз, тяжело индексировать под векторизацию (numpy-матрица характеристик строится через дорогой pivot).
2. **Типизированные определения атрибутов + JSONB с GIN-индексом.** Таблица `AttributeDefinition` (код, человекочитаемое имя, тип: `bool`/`int`/`enum`/`date`, опционально enum-варианты, применимость — ко всем/к конкретным типам нарядов или ролям), значения хранятся в `Person.attributes JSONB` (или отдельная таблица `PersonAttributeValue` с `person_id, definition_id, value_jsonb`), с GIN-индексом на JSONB для точечных фильтров и валидацией типа на уровне сервиса (Pydantic) при записи.
   - Плюсы: гибкость EAV (не нужно ALTER TABLE на каждую новую характеристику) без потери типизации (тип объявлен в `AttributeDefinition`, а не выведен из значения); GIN по JSONB даёт приемлемую скорость точечных запросов ("кто имеет X=true"); при построении снимка для `allocation` достаточно один раз выгрузить `AttributeDefinition` (маленькая таблица, кэшируется) + JSONB-значения батчем — конвертация в numpy-векторы делается в `scheduling`/`allocation` при сборке снимка, а не на каждый запрос в БД.
3. **Жёсткая схема с ALTER TABLE под каждую новую характеристику.** Быстрее всего для фиксированного, заранее известного набора.
   - Минусы: противоречит формулировке "расширяемые" и требованиям open-questions (список характеристик ещё не согласован с заказчиком) — любое изменение требует миграции и релиза `personnel`.

## Решение

**Типизированные определения атрибутов (`AttributeDefinition`) + значения в JSONB с GIN-индексом**, в сервисе `personnel`. `AttributeDefinition` определяет: код (используется как ключ в JSONB и как имя признака в векторе `allocation`), тип (`bool`/`int`/`enum`/`date`), опционально — к каким типам нарядов/ролей относится требование (чтобы UI мог отрисовать нужные поля при создании DutyType). Значения — `PersonAttributeValue(person_id, definition_id, value)`, где `value` — типизированный JSONB (`{"v": true}` / `{"v": 12}` / …), с GIN-индексом по `(definition_id, value)` для точечных фильтров в CRUD-сценариях (не для основного пути распределения — там данные уходят через batch-снимок и векторизуются один раз, как описано в `docs/allocation-design.md`, уровень 1).

Валидация типов и допустимых enum-значений — на уровне Pydantic-схем `personnel` при записи, не полагаемся на ограничения PostgreSQL для JSONB содержимого.

**Отклонено:**
- Чистый EAV без типизации — усложнил бы именно тот код, который важнее всего сделать быстрым и простым: сборку матрицы признаков для векторного фильтра в `allocation`.
- Жёсткая схема — противоречит требованию расширяемости и текущей неопределённости состава характеристик (см. `docs/open-questions.md`).

## Последствия

- Добавление новой характеристики — операция в `personnel` без миграции схемы `Person` (только вставка строки `AttributeDefinition`).
- `allocation` получает в снимке уже развёрнутый по колонкам числовой/булев вектор характеристик на человека (сборка — на стороне `scheduling` при формировании снимка, где `AttributeDefinition` кэшируется), а не JSONB — движок не работает с JSON напрямую.
- **Должность** не хранится как характеристика. Это отдельный справочник `Position` в `personnel` и поле `Person.position_id`, потому что должность участвует одновременно в требованиях ролей (ADR-0009) и в лимитах нарядов. Звание по-прежнему живёт в справочнике `Rank` сервиса `org`.
- Требования роли (мин. звание, характеристики, допустимые должности) проверяются **при выдаче допуска**, а не в движке распределения (ADR-0009). Характеристики используются для предупреждений в UI и отчётов о несоответствии, в основной путь `allocation` они не попадают.
- Допуски (`Clearance`) в новой системе тоже допускают привязку не только к `DutyType` целиком, но и к конкретной роли внутри него (см. `docs/allocation-design.md`), что требует небольшого расширения модели допуска по сравнению с legacy `DutyClearance`.
