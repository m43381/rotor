# 0016. Управление операторами через `auth-admin`

## Статус
Принято (2026-09-28, план фазы 7, шаг 7a)

## Контекст

Операторов создаёт администратор, самостоятельной регистрации нет (ADR-0002). До фазы 7 их заводили в консоли Keycloak:
- нужен доступ к администратору master-realm;
- ограничений по зоне ответственности нет;
- аудита системы нет.

По open-questions №59 администратор подразделения должен управлять операторами своего поддерева, но выдавать роли не выше разрешённых. Пароли и сессии — по №61.

## Варианты

1. **Консоль Keycloak с тонкой настройкой прав (fine-grained admin permissions).** Права задаются в Keycloak по группам.
   - Минусы: дерево подразделений придётся дублировать группами Keycloak; правило «администратор — только для нижестоящих» так не выразить; аудит остаётся в Keycloak, вне журнала системы.
2. **Сервис `auth-admin` поверх Keycloak Admin REST API** (как в ADR-0002).
   - Плюсы: права проверяются той же политикой и деревом, что во всех сервисах; изменения попадают в журнал системы; интерфейс свой.
   - Минусы: ещё один сервис и служебная учётная запись с правами на пользователей.

## Решение

**Вариант 2.**

**`auth-admin`** — FastAPI без собственных пользователей:
- **Своя БД** — только `audit_log` и `outbox`: изменения уходят в сводный журнал событием `audit.recorded`.
- **Подразделения** в зоне ответственности берутся у `org` от имени оператора (ADR-0014).
- **Права** (№59):
  - суперадминистратор — всё;
  - администратор подразделения — операторы и наблюдатели в своём поддереве, администраторы — только для нижестоящих подразделений;
  - суперадминистраторов он не создаёт и не меняет;
  - при изменении проверяются и текущие, и новые роль и подразделение;
  - себе нельзя сменить роль или подразделение и нельзя заблокировать себя.
- **Удаления нет** — только блокировка (с завершением сессий): автор изменений в журналах должен оставаться.
- **Новый оператор и сброс пароля** — 12-символьный временный пароль, показывается один раз; при первом входе Keycloak требует задать свой (`UPDATE_PASSWORD`). В журнал пароль не попадает.
- **Служебный клиент** `dutyflow-auth-admin` — конфиденциальный, только client credentials. Права в `realm-management`:
  - `manage-users`, `view-users`, `query-users`;
  - `view-realm` — чтение настроек. Без него Keycloak не отдаёт состав ролей (`/roles/{role}/users`), и список из 5 000 операторов пришлось бы собирать запросом на каждого.
- **Настройку Keycloak** на уже развёрнутом стенде выполняет одноразовый контейнер `keycloak-init` (`python -m auth_admin.bootstrap`) при каждом `up`, идемпотентно. Он заводит служебный клиент с секретом из `AUTH_ADMIN_CLIENT_SECRET` и применяет политику паролей и блокировок (№61). Импорт realm-файла Keycloak выполняет только при первом создании realm, поэтому такие изменения через импорт не доходят до существующих инсталляций.

## Последствия

- Администратору master-realm Keycloak больше не нужен повседневный доступ: он используется только `keycloak-init`.
- Если IdP заменят (ADR-0002), меняются `auth_admin.keycloak` и `bootstrap`; API операторов и интерфейс остаются.
- Секрет служебного клиента — в `deploy/.env` (создаёт `just env`), в репозитории его нет.
- Список операторов собирается в памяти: все пользователи постранично и состав четырёх ролей. На 5 000 учёток это единицы запросов к Keycloak; проверяется нагрузочным прогоном (шаг 7d).
