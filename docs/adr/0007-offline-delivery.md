# 0007. Офлайн-сборка и поставка

## Статус
Принято

## Контекст

Система работает в изолированной сети без доступа в интернет (`CLAUDE.md`: "никаких CDN, внешних шрифтов, телеметрии и обращений в интернет во время работы. Все ассеты собираются в образ"). Это касается не только рантайма, но и процесса сборки/поставки: целевая среда, скорее всего, не имеет доступа ни к Docker Hub, ни к PyPI, ни к npm registry, ни к apt-репозиториям.

Целевая платформа (`docs/open-questions.md` №17–18): обычный Linux с Docker и Docker Compose. Требований к отечественной ОС и сертификации пока нет. Клиентские места работают в свежих Chromium/Firefox (версии не старше 2–3 лет).

## Варианты

1. **`docker save`/`docker load`** — образы собираются на машине с доступом в интернет, экспортируются в tar-архивы, переносятся (флешка/защищённый канал) и загружаются в целевой контур через `docker load`.
   - Плюсы: не требует поднимать инфраструктуру registry на закрытом контуре; знакомый и хорошо документированный процесс; работает с `docker compose` без изменений (образы уже есть локально у `docker load`).
   - Минусы: версионирование образов вручную (нужна дисциплина именования тегов и хранения архивов), нет push/pull воркфлоу для обновлений (каждое обновление — заново собрать/перенести/загрузить).
2. **Локальный Docker registry** на закрытом контуре (`registry:2` образ, тоже перенесённый через `docker save`/`load` один раз), дальше `docker push`/`pull` внутри контура.
   - Плюсы: привычный push/pull воркфлоу для обновлений после первого переноса; можно версионировать и откатываться через теги в самом registry.
   - Минусы: ещё один компонент, требующий эксплуатации (TLS/сертификаты для registry, хранение), не нужен на масштабе одного дипломного/пилотного стенда.
3. **Полностью офлайн-сборка внутри контура** (все wheels/npm-пакеты предзагружены, `pip install --no-index`, `npm ci --offline`, сборка образов происходит уже в контуре из исходников).
   - Плюсы: не нужно передавать собранные образы, только исходники + кэш зависимостей — меньше объём переноса, легче делать security review переносимого содержимого (весь код виден).
   - Минусы: требует переносить и поддерживать актуальным кэш всех зависимостей (Python wheels, npm-пакеты, возможно deb-пакеты базового образа) отдельно от кода; сборка занимает время на каждом развёртывании.

## Решение

Комбинация: **офлайн-кэш зависимостей** (wheels для `uv`, npm-кэш для фронтенда) переносится и коммитится/хранится в `tools/`/`deploy/` инфраструктуре (не в основном репозитории кода — отдельный артефакт переноса), сборка образов происходит в CI на машине с доступом в интернет, готовые образы переносятся через **`docker save`/`docker load`** (вариант 1) как основной механизм поставки на закрытый контур. Локальный registry (вариант 2) — не первая необходимость: на масштабе одного развёртывания это лишний компонент; фиксируется как возможное будущее расширение, если появится несколько независимых закрытых контуров, которым нужно раздавать обновления централизованно.

Обоснование:
- `docker save`/`load` — минимальный по числу движущихся частей процесс, соответствует принципу "меньше компонентов на закрытом контуре" (тот же принцип, что и в ADR-0004 про выбор Redis Streams вместо RabbitMQ/NATS).
- Полностью офлайн-сборка в контуре (вариант 3) избыточна, если сам контур не имеет средств сборки (компиляторов, etc.) как политики безопасности — типичное требование для закрытых контуров: минимизировать исполняемый в контуре tooling, поставлять уже собранные артефакты.

## Последствия

- CI-пайплайн должен производить: собранные Docker-образы всех сервисов + frontend, экспортированные `docker save` в tar; `.env.example` без секретов; `docker-compose*.yml`; Keycloak realm export; список версий образов (манифест переноса).
- Реальные секреты (пароли БД, ключи подписи JWT, TLS-ключи внутреннего CA) **не** попадают в переносимый артефакт — генерируются или вводятся оператором на месте разворачивания (соответствует правилу `CLAUDE.md` #7: "секреты не коммитятся, в репозитории только `.env.example`").
- Обновление системы на закрытом контуре — процесс "перенеси новые tar-архивы → `docker load` → `docker compose up -d`" — должен быть описан как runbook в `deploy/README.md` на фазе, когда появится первый деплоймент (см. `docs/roadmap.md`).
- Фронтенд собирается под таргет ES2020 без полифиллов. Шрифты, иконки и все ассеты PrimeVue/ECharts лежат в бандле.
- Если позже потребуется Astra Linux или РЕД ОС, базовые образы сервисов не меняются: меняется только хост-ОС, где нужно проверить поддержку Docker. В режиме замкнутой программной среды («Смоленск») может понадобиться подпись бинарников или отказ от Docker; это отдельный ADR-пересмотр.
- k8s прямо сейчас не нужен (`CLAUDE.md`), поэтому этот ADR ограничен `docker compose`-поставкой; при переходе на k8s потребуется отдельный ADR (образы `save`/`load` там заменяются на `ctr image import`/аналоги, компоуз — на манифесты).
