# Дизайн движка распределения

Мотивация и выбор подхода на верхнем уровне — ADR-0006. Этот документ — детальный дизайн воронки, обоснование известности каждого метода и его асимптотики (материал рассчитан на прямое использование в пояснительной записке).

## Общая идея — воронка

На входе — потенциально огромная задача (десятки тысяч человек, тысячи ячеек `дата × тип наряда × роль`). Идея воронки: **чем шире задача, тем дешевле должна быть операция над ней**; по мере сужения (декомпозиция по дереву → отсев по допустимости → отсев по ёмкости) подключаются всё более точные и дорогие методы, потому что к этому моменту подзадача уже маленькая. Это стандартный паттерн в промышленных решателях (например, поисковые системы: дешёвый bitmap-фильтр кандидатов → дорогой ранжирующий скоринг только на прошедших фильтр; или СУБД: index scan сужает набор строк перед дорогим join/sort).

## Уровень 0. Иерархическая декомпозиция

Задача делится по дереву подразделений: верхний уровень распределяет ячейки между дочерними подразделениями (см. уровень 4 ниже — пропорциональное представительство + min-cost flow), каждое подразделение решает свою подзадачу внутри себя (см. уровень 4 — CP-SAT/Hungarian/greedy+LS в зависимости от размера). Это не только алгоритмическая оптимизация — это соответствует **реальному организационному процессу** делегирования, унаследованному из legacy (`docs/legacy-analysis.md` §2.2, §5): вышестоящее подразделение физически не может и не должно распределять людей нижестоящего, оно передаёт ему ячейку и требование, а нижестоящее решает локально.

**Асимптотика:** декомпозиция превращает одну задачу размера `N` (люди) × `M` (ячейки) в `k` подзадач меньшего размера — при равномерном дереве глубины `d` и ветвлении `b`, размер подзадачи на листовом подразделении ~ `N/b^d`. Это ключевое свойство, которое делает применимыми точные методы (CP-SAT, венгерский алгоритм) на нижних уровнях — на всей организации целиком они были бы неприменимы по времени.

## Уровень 1. Жёсткие ограничения, векторно

Один раз пакетно загружаем снимок данных (через batch-эндпоинты `org`/`personnel`, собранные `scheduling` — см. `docs/architecture.md` §4), дальше всё — в памяти, никаких повторных запросов к БД (устраняет главный класс проблем legacy: `_calculate_capacity` и `_recent_penalty`, вызывавшиеся построчно на каждую пару "подразделение×дата"/"человек×ячейка", см. `docs/legacy-analysis.md` §4.1–4.2).

Матрицы numpy:
- `C[P, K]` (`uint64` битовые маски или `bool`) — допуски людей `P` к ролям нарядов `K` (допуск всегда выдаётся на роль, ADR-0009). Битовая маска — тот же принцип, что bitmap-индексы в колоночных СУБД (Oracle bitmap index, Postgres используются похожие идеи в GIN): проверка "обладает всеми нужными допусками" превращается в одну битовую операцию `AND` + сравнение, вместо построчного перебора.
- `A[P, T]` (`bool`) — доступность человека по дням `T`: освобождения (интервалы дат) переводятся в маску `False` на занятые интервалы один раз векторно (`np.zeros` + срезы по индексам дат начала/конца), а не построчными SQL-запросами по дате, как в legacy `_calculate_capacity`, который для каждой даты заново фильтровал `exemptions__date_from__lte / date_to__gte`.
- `valid[P, K, T]` — срок действия допуска. Хранится как интервалы `valid_from`/`valid_to` и разворачивается в маску векторно, как освобождения.

Допустимость кандидата для роли `k` определяется **только действующим допуском** (ADR-0009). Требования роли (мин. звание, характеристики, должность) проверяются в `personnel` при выдаче допуска. Допуск, выданный вопреки требованиям (`overrides_requirements`), для движка равноправен обычному: решение оператора важнее требований.
```
E[P, K, T] = C[P, K]                          # есть допуск к роли
           & valid[P, K, T]                   # допуск действует на дату (valid_from/valid_to)
           & A_cell[P, K, T]                  # человек свободен во все сутки, которые занимает ячейка (ADR-0008)
```
Поскольку наряд может длиться несколько суток (ADR-0008), доступность для ячейки — это `AND` маски `A[P, ·]` по всем занятым суткам экземпляра. Вычисляется векторно сдвигами `A` на `0..d-1` дней, где `d` — число занятых суток.

Векторы звания `R[P]` и характеристик `Attr[P, F]` в снимок движка **не входят**. Они используются только в `personnel` (предупреждения при выдаче, отчёт о несоответствиях).

> **Изменено 2026-09-26** (ответы на `docs/open-questions.md` №6–7): прежняя формула проверяла в движке звание и характеристики. Это противоречит правилу «допуск важнее требований», поэтому проверка перенесена в момент выдачи допуска.
**Стоимость: O(P·K)**, без циклов на Python — векторные операции numpy выполняются в скомпилированном коде, что на практике на 2–3 порядка быстрее эквивалентного Python-цикла с ORM-запросом внутри (что и было главной проблемой legacy).

## Уровень 2. Проверка выполнимости и ёмкость

Ёмкость по ролям и дням — одно матричное умножение:
```
cap[K, T] = Eᵀ · A     # (K×P) · (P×T) = (K×T)
```
Каждый элемент `cap[k, t]` — число людей, одновременно допустимых к роли `k` и доступных в день `t`. **Стоимость: O(K·T·P)** одной операцией BLAS (numpy использует оптимизированные матричные библиотеки) — вместо `O(units × dates)` отдельных ORM-запросов, как в legacy `_calculate_capacity`, вызывавшемся **дважды на каждую пару unit×date** (см. `docs/legacy-analysis.md` §4.1).

Дефициты (`cap[k,t] < required[k,t]`) находятся заранее, до попытки решения, и объясняются человеческим языком ("14-го не хватает 2 человек с допуском X в подразделении Y") — это возможно именно потому, что `cap` уже посчитан целиком одной операцией, а не по частям в процессе жадного прохода.

Для строгой проверки выполнимости с учётом того, что один человек не может закрыть две роли одновременно (ёмкость по столбцам — верхняя граница, не гарантия), применяется **проверка условия Холла через max-flow**: строится двудольный граф человек↔(роль,день), пропускная способность рёбер — допустимость, ищется максимальный поток; если максимальный поток меньше суммарной потребности — задача невыполнима строго, и это точный (не эвристический) вывод. Это стандартный результат теории паросочетаний (теорема Холла о свадьбах / König) — переносится на многодневную многороличную задачу через построение сети с истоком → людьми → (роль,день)-парами → стоком.

## Уровень 3. Скоринг, векторно

Для каждого кандидата — вектор признаков (не скаляр "score" как magic number, а именно вектор, сохраняемый для объяснимости):
- нагрузка с **экспоненциальным затуханием за скользящее окно** (не обнуление каждый месяц, как в legacy `_build_person_month_load`, а `load(p) = Σ_i w^(now - date_i) · duty_weight_i`, где `w < 1` — коэффициент затухания, `date_i` — даты прошлых нарядов вне зависимости от границ месяца). Экспоненциальное скользящее среднее — стандартный подход в теории управления запасами/расписаниями именно для того, чтобы "забывать" старую нагрузку постепенно, а не резким обнулением, которое создаёт несправедливость на стыке периодов (проблема legacy, `docs/legacy-analysis.md` §4.5, за исключением частично корректного `_recent_penalty`, который эту идею уже интуитивно нащупал, но только для соседних двух дней);
- нагрузка по конкретному типу наряда (аналогично, с затуханием);
- **отдельный счётчик нарядов в выходные/праздники** (со своим затуханием) и вес таких нарядов > 1 в общей нагрузке. Праздничные наряды выравниваются между людьми отдельно, а не только утяжеляют общую сумму (ответ на `docs/open-questions.md` №10). Используется производственный календарь из `org`; для многосуточного наряда праздничность считается по каждым занятым суткам;
- единица нагрузки — **нарядо-сутки** (число занятых суток экземпляра, ADR-0008), а не штуки: наряд на 72 ч тяжелее наряда на 6 ч;
- давность последнего наряда (количество дней с последнего назначения — используется вместо жёсткого "вчера/позавчера" из legacy для более гладкого штрафа за близость нарядов);
- "долг" подразделения — накопленное отклонение от справедливой доли по ёмкости за прошлые периоды (входит и в скоринг человека, и в уровень 4 при распределении между подразделениями).

Стоимость: `cost = X · w`, где `X[P, F]` — матрица признаков, `w[F]` — веса, **вынесенные в конфигурацию** (YAML/JSON, не константы класса, как в legacy — прямое устранение проблемы §4.6 `docs/legacy-analysis.md`, включая явное требование, чтобы скоринг **реально управлял выбором**, а не служил слабым тай-брейкером после набора жёстко упорядоченных счётчиков, как это де-факто было в `PlanAutomationService`). **Стоимость: O(P·F)** — снова одно матричное умножение вместо Python-цикла.

## Уровень 4. Оптимизация — метод по размеру подзадачи

### Распределение ячеек между подразделениями (верхний уровень декомпозиции)

Единица распределения — ячейка `дата × наряд × роль` (делегирование по ролям, ADR-0009). Квоты и ёмкость считаются отдельно по каждой роли, поэтому дежурного и дневальных одного наряда могут дать разные подразделения.

Квоты подразделений — **методы пропорционального представительства** (Сент-Лагю или наибольший остаток Гамильтона), которые в оригинальной постановке решают задачу "поделить целочисленные места пропорционально голосам" (парламентские выборы) — здесь роль "голосов" играет **ёмкость** подразделения (не численность!, что отдельно устраняет проблему legacy: балансировка "по структуре" в `balanced_structure` игнорировала фактическую кадровую ёмкость, а "по ёмкости" `balanced_capacity` использовала её только как порог допустимости 0/1, не как вес квоты), с поправкой на накопленный долг прошлых периодов. Оба метода (Сент-Лагю, метод Гамильтона) — классические, с доказанными свойствами (Сент-Лагю не имеет "парадокса Алабамы", хорошо изучен в теории справедливого деления, применяется в реальных избирательных системах — поэтому его свойства предсказуемы и объяснимы в пояснительной записке).

После того, как квоты по подразделениям на месяц определены, **расстановка по конкретным датам** внутри квоты — задача **min-cost flow**: узлы-источники (подразделения с квотой как ёмкостью ребра), узлы-стоки (даты с требованием), стоимость ребра — скоринг (уровень 3) с учётом дневной/недельной нагрузки. Min-cost flow — полиномиальный точный алгоритм (это в точности транспортная задача линейного программирования, для которой существуют комбинаторные полиномиальные алгоритмы, например successive shortest paths через SPFA/Dijkstra с потенциалами) — даёт оптимум по суммарной стоимости за полиномиальное время, без эвристик на этом шаге.

### Большие подзадачи (нет времени на точный решатель)

**MRV (most constrained first)** — эвристика из теории CSP (Constraint Satisfaction Problem): среди ещё не заполненных ячеек первой заполняется та, у которой **меньше всего допустимых кандидатов** (наименьший remaining-value domain). Эта эвристика — стандартный и хорошо изученный приём для CSP (используется, например, в решателях судоку и в классическом планировании расписаний): интуиция в том, что откладывание самых "зажатых" ячеек на потом почти всегда приводит к тупику (нет кандидатов вообще), тогда как их обработка первыми, пока выбор ещё широк для остальных, минимизирует риск. Это прямое устранение проблемы legacy "жадный алгоритм по датам съедает лучших кандидатов в начале месяца" (§4.4 `docs/legacy-analysis.md`) — вместо порядка "по календарю" используется порядок "по стеснённости", что структурно устойчивее к недокомплекту в конце периода.

После получения жадного (пусть не оптимального) решения по MRV — **локальный поиск** с ограничением по времени: swap двух назначений между собой (если оба остаются допустимыми и суммарная стоимость снижается), simulated annealing (допускает временное ухудшение с убывающей вероятностью, чтобы выбраться из локального минимума) или tabu search (запрещает возврат к недавно посещённым состояниям). Это стандартные метаэвристики для комбинаторной оптимизации, применяемые именно тогда, когда точный решатель не укладывается по времени, а качество жадного решения нужно улучшить без гарантии оптимума.

### Один день внутри подразделения

Задача о назначениях (assignment problem) — классическая постановка: `n` людей × `n` ролей/слотов, матрица стоимости, найти паросочетание с минимальной суммарной стоимостью. Решается точно **венгерским алгоритмом** (`scipy.optimize.linear_sum_assignment`) или эквивалентно через min-cost flow — за **O(n³)**, что на малом `n` (один день, одно подразделение — десятки-сотни людей) — доли секунды, и это **гарантированный глобальный оптимум**, а не эвристика.

### Месяц внутри подразделения (до ~200–300 человек)

Типичный размер (`docs/open-questions.md` №5): 5–20 нарядов в сутки на подразделение, то есть десятки ячеек «наряд × роль» в сутки и порядка 300–1 500 ячеек в месяц. Это основной рабочий диапазон CP-SAT, поэтому его производительность на таких размерах — ключевая цель бенчмарка.

**OR-Tools CP-SAT** — классическая постановка Nurse/Employee Rostering Problem (NRP), одна из самых изученных задач CSP/CP в исследовании операций (десятки лет литературы, стандартные бенчмарки INRC — International Nurse Rostering Competition). Жёсткие ограничения (подтверждены заказчиком, `docs/open-questions.md` №8, №9, вопрос 23):
- **не больше одного наряда в сутки** на человека: для каждого человека и каждых суток сумма переменных ячеек, занимающих эти сутки, ≤ 1;
- **минимальный отдых** `rest_hours` между концом одного наряда и началом следующего (ADR-0008). В legacy это был мягкий штраф, здесь это ограничение модели: пары ячеек, нарушающие отдых, объявляются взаимоисключающими (`AddAtMostOne` / `AddBoolOr`);
- **лимиты нарядов** на человека за период (`DutyLimit`: по подразделению, званию или должности), если они заданы;
- закреплённые ячейки (pin — ограничение «переменная = константа»). Ручное назначение с `rest_override` — тоже pin: движок его не пересматривает, но в отчёте показывает как нарушение отдыха, допущенное оператором. Целевая функция — минимизировать максимальную нагрузку (min-max, справедливость по худшему случаю) и/или сумму квадратов отклонений от средней нагрузки (штраф за неравномерность растёт быстрее линейного — классический приём для поощрения равномерности без жёсткого min-max, который может быть избыточно консервативным).

Жадное решение (MRV, тот же метод, что для больших подзадач) передаётся решателю как **hint** (`AddHint` в CP-SAT) — это ускоряет поиск (решатель стартует не с нуля, а с уже допустимой точки) и даёт осмысленный fallback, если решатель не успевает за отведённый **таймаут**. Если задача невыполнима с жёсткими ограничениями — мягкие ограничения ослабляются (например, минимальный отдых временно нарушается для конкретной пары ячеек), и в отчёте перечисляется **что именно нарушено и почему** (какое ограничение, для кого, на сколько) — прямое продолжение идеи explainability, начатой на уровне 2 (дефициты) и уровне 3 (векторы признаков).

### Скользящий горизонт

Хвост прошлого месяца (последние `k` дней, `k` ≥ `max(duration) + max(rest_hours)` в сутках, потому что многосуточный наряд, начатый в конце месяца, занимает первые числа следующего, ADR-0008) фиксируется как **контекст**, а не как переменные модели — назначения из хвоста участвуют в проверке ограничений отдыха (нельзя поставить 1-го числа человека, который стоял 31-го), но не пересматриваются текущим прогоном. Это устраняет проблему legacy "справедливость и ограничения не видят границу месяца" при сохранении помесячной публикации графиков (`Schedule.status = published` по месяцам, унаследовано из legacy как рабочая единица планирования).

## Требования к движку (сквозные, для всех уровней)

- **Детерминизм**: одинаковый вход (снимок + конфигурация) и `seed` (для стохастических частей — simulated annealing, тай-брейки при равенстве скоринга) всегда дают одинаковый выход. Требование CLAUDE.md #6 — необходимо для тестируемости, воспроизводимости бенчмарков и разбора инцидентов ("почему во вторник система поставила именно этого человека").
- **Ручные закрепления (pin)**: уважаются на всех уровнях воронки как жёсткое ограничение (переменная фиксирована), включая уровень 4 (CP-SAT видит pin как `AddHint`+`Add(var == value)`, MRV/LS не трогает закреплённые ячейки).
- **Объяснимость**: для каждого назначения сохраняется — вектор признаков (уровень 3), место среди кандидатов (ранг по скору), причины отсева остальных кандидатов (какое условие уровня 1/2 не прошли, либо проиграли по скору). Хранится в БД `scheduling`, не только в ответе API (в отличие от legacy, где top-5/top-10 существовали только в preview-ответе, см. `docs/legacy-analysis.md` §4.6).
- **Предпросмотр → применение**: движок (`allocation`) только считает и возвращает решение; запись — отдельный шаг в `scheduling`, фиксирующий только изменившееся (тот же контракт, что в legacy `preview_distribution`/`apply_distribution` и `preview_assignments`/`apply_assignments`, формализованный как обязательное свойство новой системы, см. `docs/architecture.md` §3.3–3.4).
- **Не зависит от БД**: вход — сериализуемый снимок (JSON/Arrow), выход — сериализуемое решение; тестируется и бенчмаркается без поднятия сервисов и БД.

## Экспериментальная часть (для диплома)

**Генератор синтетических данных** (`tools/gen`): параметры — число людей (1k / 5k / 20k / 50k), глубина и ветвление дерева подразделений (основной профиль по ответу заказчика — **6+ уровней, тысячи узлов**), длительности нарядов (от часов до нескольких суток), доля допусков, выданных вопреки требованиям, число типов нарядов и ролей, плотность допусков/характеристик, реалистичное распределение освобождений. Детерминирован по seed (тот же принцип, что и у движка).

**Стенд сравнения** (`tools/bench`): four-way сравнение на одинаковых синтетических датасетах —
1. **legacy-жадный** (портированный как baseline без сетевого/ORM оверхеда — тот же алгоритм из `PlanAutomationService`/`AssignmentAutomationService`, но на снимке в памяти, чтобы сравнение было честным по алгоритму, а не по инфраструктуре);
2. **MRV + локальный поиск**;
3. **венгерский алгоритм** (по дням);
4. **OR-Tools CP-SAT** (по месяцам, там где размер подразделения позволяет).

**Метрики:**
- время выполнения, потребление памяти (по размеру датасета — для демонстрации асимптотики на практике, не только в теории);
- недокомплект (число незакрытых ролей/ячеек);
- нарушения ограничений (мягких — отдых, лимиты; с указанием, сколько и какой тяжести);
- справедливость: стандартное отклонение нагрузки, коэффициент Джини, индекс Джайна (fairness index, стандартная метрика из сетевых технологий, хорошо переносится на распределение нагрузки), разброс `max − min`.

Результаты стенда — прямой материал для главы диплома "экспериментальное сравнение подходов", с готовым обоснованием, почему каждый метод применяется на своём уровне размера задачи (уже изложено выше по каждому уровню).

## Реализация (фаза 4)

Код — `services/allocation/src/allocation/engine`, чистые функции над numpy и scipy, без БД и HTTP.

| Уровень | Модуль | Как сделано |
|---|---|---|
| 0 | `people.py`, `units.py` | Два вида задачи. **Люди** — ячейки, которые закрывает само подразделение графика, заполняются людьми его поддерева. **Подразделения** — свои ячейки отдаются прямым дочерним подразделениям. Ручные и закреплённые назначения всегда фиксированы; в режиме `rebuild` движок пересматривает только свои незакреплённые (open-questions №41). |
| 1 | `feasibility.py`, `state.py` | Статическая допустимость (допуск и его срок, освобождение во все занятые сутки) — векторно по всем людям. Динамическая — массивы [люди × дни]: `busy` («≤ 1 наряда в сутки»), `rest_until` и `starts` (отдых до и после наряда за одно окно 31 сутки), счётчики месяца для лимитов. |
| 2 | `feasibility.py` | Ёмкость ячеек и дефициты с объяснением до решения. Строгая верхняя граница — максимальный поток «исток → человек → (человек, день) → ячейка → сток» (`scipy.sparse.csgraph.maximum_flow`), граф строится векторно. |
| 3 | `state.py` | Признаки кандидата: нагрузка с экспоненциальным затуханием (полураспад 30 дней, №42) в нарядо-сутках × вес наряда, в выходной × 1,5 (№43); нагрузка по типу наряда; счётчик праздничных нарядов; близость к другому наряду. Для подразделений — выбранная доля квоты, занятость в этот день, запас людей. Веса — `allocation/config/default.yaml`, переопределяются на прогон. |
| 4 | `people.py`, `units.py` | Жадный выбор в порядке MRV (сначала ячейки с меньшим числом допустимых кандидатов), равенство — детерминированный жребий по seed. Для подразделений квота по каждой роли — пропорционально ёмкости с поправкой на прошлую нагрузку (метод наибольшего остатка); квота соблюдается, пока есть подразделения, не выбравшие её. |

Объяснимость: у каждого решения признаки, стоимость, число допустимых кандидатов, пять ближайших альтернатив с признаками и сводка отсева (нет допуска, освобождён, занят, отдых, лимит). Детерминизм: `solution_hash` — SHA-256 решения без замеров времени.

Интеграция (фаза 4b): scheduling собирает снимок, вызывает `POST /internal/solve`, хранит прогон и объяснения; применение сверяет hash свежего снимка с сохранённым и отклоняет устаревший прогон. На демо-стенде расчёт для курса (72 человека, 68 мест) от нажатия кнопки до панели предпросмотра — около 1,2 с.

Проверка: независимая реализация правил простым перебором (`engine/verify.py`) сверяет каждое решение в тестах свойств на случайных снимках (`allocation.synthetic`) и в бенчмарке. Результаты — `docs/benchmarks/allocation.md`. Самое заметное: построение графа для максимального потока циклом на Python занимало 9,7 с на 20 тыс. человек, векторное — 0,4 с.
